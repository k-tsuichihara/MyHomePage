# ローカル完全削除・ゴミ箱一括削除の契約とテスト方針

PR #18の承認、Review8§3・4・5・7とv3追加契約に基づく。旧版の全削除（旧キーへ[]）とは異なり、ゴミ箱内だけを対象とする。旧キー・migration・legacySnapshotは変更しないため、全コピーからの内容消去を保証しない。

## APIと書込境界

- ストアのdeletePermanentlyはid/expectedRevision/requestId、emptyTrashはtargets（id/revisionの全組）/requestIdを受ける。通常操作と同じrequestId集合に、入力検証・最初のawaitより前に予約し、拒否・結果不明・0件でも解除しない。入力値は受付時に独立した値へ固定する。
- 直接APIを使う呼出側にも明示操作が必要。UIはcontrollerの世代付き確認を必ず経由する。自動削除・状態操作経由の削除は提供しない。

### 利用者確認と低レベルAPIの責務境界

利用者の確認を強制する境界はcontrollerのdispatchである。store.deletePermanently／emptyTrashはその内部実行ポートで、確認チケットを検証するAPIではない。requestId・ID・revisionが正しくても、それは利用者確認の証明にはならない。低レベルポートを直接呼べる信頼済みコードに対する、確認迂回防止の認証機構や能力トークンは実装していない。

現在の製品srcでこれらを呼ぶのはlocal-memo-controller.tsだけであり、UIのmountMemoPreviewにはdispatch/getStateだけを持つcontrollerを渡す。隔離fixtureのpreview-memoryラッパーは遅延・障害試験の委譲ポートで、独自に削除開始しない。実ブラウザfixtureもcontroller.dispatchを使う。低レベルAPIを直接呼ぶ単体テストは保存処理自体を検証するためのもので、利用者確認まで保証する試験ではない。

製品接続・他機能追加時も、UI・イベント・自動処理へストア／データ層の削除ポートを公開しないこと、controller以外に新たな呼出箇所がないことを設計・差分レビューで確認する。ストア単体でも確認を強制する保証が必要になった場合は、別途API設計として合意する。現在の保証をその水準へ拡大して説明しない。

境界の回帰試験はストアの実メソッドをspyし、個別／一括とも確認前・偽トークン・取消で呼出0件／書込0件、承認後は固定ID・revisionだけを1回渡すことを確認する。結果不明後のloadで旧確認を使えず、旧集合が自動拡張されないこと、新集合には別の明示確認・requestIdが必要なことも直接照合する。
- データ層の専用削除経路だけが履歴追加を許される。通常transactの履歴不変ガードは維持する。専用経路は最新v3の全体検証後に、対象メモ除去・関連除去・原表記のID追加を同じJSONへまとめ、一度だけ書いて読戻す。
- v2／pending／未知版／破損／旧値のみ／ロック非対応は未書込拒否。形式更新・移行・復旧を暗黙に実行しない。ストアは生成時の保存先に固定し、後の依存差替えで確認を別領域へ流さない。

## 対象照合と確認

- 個別はゴミ箱内の存在とrevision一致を要求する。不在・復元・更新済みなら停止。安全整数の最大revisionも削除時に加算しないため受理できる。
- 一括はフィルター結果ではなくゴミ箱全件。大小文字同値のUUID・revisionの集合を順序に依存せず照合し、重複・増減・復元・更新は全件拒否する。0件一致ならnot-needed/count=0、書込0件。タグ・通常メモ・対象外関連・既存履歴は保持する。
- 確認は操作種別・固定ID/revision・controller世代・一つのストア寿命に結び付ける。取消・再読込・編集・確認消費後に流用しない。二重確認・非同期再入は書込一件に制限する。保存先切替APIは提供しない。
- 成功後だけ再読込する。個別削除した詳細は一覧へ戻すが、後続読込失敗を削除失敗／結果不明に書き換えない。

## 失敗と再確認

書込前拒否は無変更。setItem試行後の容量例外・書込後例外・読戻し失敗はunknownとし、自動再送・旧値書戻し・初期化・履歴間引きをしない。結果不明後は明示loadによる現在状態の診断と、新しい対象・確認・requestIdが必要。元対象が不在でも過去要求を成功へ昇格しない。追加されたメモを旧対象へ勝手に追加しない。利用者が新しくゴミ箱全件の一括操作を要求した場合のみ、新しい全件集合を確認する。

## テスト観点・対象外

個別／一括正常・0件、禁止形式、通常メモ・不在・競合・重複UUID・集合増減・復元・revision上限、単一書込と他データ不変、受付後入力変更、確認取消・失効・二重操作、要求ID再利用、容量／読戻し障害、unknown後のload・新確認、削除済みID再作成拒否、旧キー／snapshot不変を合成データで検証する。

隔離メモリUIで対象件数・不可逆表示・検索外の対象・失敗表示を検証し、実ブラウザは既存の所有profile・専用loopback origin・合成データだけで複数タブ／Web Locksを確認する。全Vitest・メモリE2E・永続化／切り替え／形式更新E2E・各ビルドを回帰実行する。生成物・profile・生ログはGit除外。

本番接続・公開画面・Supabase/Auth・バックアップ復元・旧キー消去は対象外。履歴は再送台帳ではなく、サイトデータ喪失・バックアップ巻戻しまでの永久保証はしない。旧JS並行利用・導入元確認・v3対応保守版の公開・他ブラウザ・実機受入等の公開ゲートは継続する。

## 専用fixtureと実行手順

メモリUIは固定の`?scenario=delete`、`delete-slow`、`delete-quota`、`delete-unknown`、`delete-readback`だけが合成v3を持つ。通常のv2シナリオは変更せず、完全削除を表示しない。合成v3は通常データ層の厳格loadに成功した場合だけUIへ入り、v2専用移行診断へ流さない。既存移行診断のv3拒否は緩めない。

`tools/memo`で型チェック・全Vitest、`test:e2e`、`test:persistence`、`test:transition`、`test:format`を実行する。実タブ競合の追加2ケースは既存所有ガード付き`test:format`に置き、同じ対象の削除が一方だけ成功することと、実Web Locks待機中の別タブ復元で一括削除が全体拒否になることを確認する。API用合成メモリ試験の容量例外と、既存永続化試験の実容量不足を混同しない。
