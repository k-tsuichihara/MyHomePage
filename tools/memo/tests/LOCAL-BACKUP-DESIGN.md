## 2. バックアップ作成の対象と形式案

### 2.1 推奨範囲

初版は**通常利用可能なローカルv3全体のデータバックアップ**だけを対象とする。

- 通常メモ、ゴミ箱メモ、全タグ、全関連、削除済みID履歴を含める。検索・選択タグ・表示ページで範囲を減らさない。
- メモの全フィールド（日時、revision、pinnedAt、deletedAt、lastRequestIdを含む）を原値で保持する。lastRequestIdの保存は冪等性保証ではない。
- 旧キー、migration/legacySnapshot、未保存ドラフト、未解決要求内容、requestId使用済み集合、UI条件、認証情報は含めない。
- 旧キー・legacySnapshotを除外するのは、過去内容の不要な複製と別保存先への移行metadata混入を避けるため。この形式は保存領域のバイト単位の完全イメージではなく、旧データ移行の復旧資料にもならない。除外範囲を利用者へ事前表示する。
- v2・pending・未知版・破損・読取不能は作成を停止。空の履歴を補ってエクスポートしない。v2向け救出用アーカイブを将来設ける場合も別形式・別承認とし、復元可能と表示しない。
- v3でmemosが0件でも、タグや履歴を含む有効なバックアップとなる。全件数0と読み取り失敗は区別する。

### 2.2 専用ファイル形式（案）

UTF-8（BOMなし）のJSON。保存領域のversionとファイル形式のbackupVersionを独立させる。以下は合成の空データ例で、実行証跡ではない。

```json
{
  "format": "myhomepage.memo.local-backup",
  "backupVersion": 1,
  "sourceStorageVersion": 3,
  "exportedAt": "2026-01-01T00:00:00Z",
  "data": {
    "memos": [],
    "tags": [],
    "memoTags": [],
    "deletedMemoIds": []
  }
}
```

全体形式・版が解釈不能なら停止。個別不正は§4の診断・選択不可／タグ除外規則で扱う。生のv1配列、v2/v3保存JSON、形式識別子だけ書き換えたファイルは専用形式として受理しない。外部入力は§4の段階検証を適用する。出力元と保存候補のv3厳格検証は維持し、偽のmigrationで既存経緯を表現しない。

format/sourceStorageVersion/exportedAtはファイル内の自己申告であり、出所・所有者・真正性の証明ではない。日時が新しいことを優先上書きの根拠にしない。初版で署名・暗号化・真正性保証は提供しない。JSON検証は構造・整合性の確認であり、改ざん検出の保証ではない。

### 2.3 作成時の整合性

1. 明示エクスポート操作後、共通ロック内で保存先を読み、v3全体を検証する。読取だけで書込はしない。
2. 新旧キーを再確認し、整合した不変スナップショットをメモリへ確保する。現行loadは独立した値を返すが生値を公開しないため、必要な読取専用境界は実装時に設計する。
3. ロックを解放して専用JSONを生成し、同じファイル用検証器で再検証する。実際に生成したBlobのUTF-8内容・サイズも確認する。
4. 利用者操作でファイル保存を開始する。OSの保存ダイアログ中はロックを保持しない。

保証は取得時点のスナップショットで、ダウンロード完了時の最新状態ではない。ブラウザが保存開始したことと、利用者のディスクへ確実に保存できたことを区別する。失敗・取消時に「バックアップ保存済み」と断定しない。

## 3. 復元方式の比較と最新合意

[最新合意](https://github.com/k-tsuichihara/MyHomePage/pull/19#issuecomment-6539817551)を優先する。手動localStorage JSONエクスポート／インポート。自動定期バックアップは不要。主目的は端末・ブラウザ間の移行と消失対策。

| 方式 | 最新の扱い |
|---|---|
| ①追加型統合 | 選択正常メモを全て新UUIDで追加、全正常タグを統合。既存メモ・タグは変更／削除しない |
| ②過去状態復元 | 完全削除後の単件回復は§4.4.1を維持。①とは別機能で、既存タグだけ参照する |
| ③初期復元 | 空保存先の具体仕様はオーナー判断待ち・保留。①の新UUID・日時初期化を無条件適用しない |
| 完全置換・無制限上書き | 採用しない。既存内容・履歴を巻き戻す危険がある |

旧①の元ID保持・同ID差分全体拒否・一致行スキップ・履歴単純和集合案は撤回する。3方式完成の要件は維持し、①だけで完成と判定しない。

## 4. 追加型統合の決定事項と影響

### 4.1 事前検証・一覧・選択

- JSON全体を解釈不能なら中断。全体検証と行単位検証を分け、不正メモは一覧に残して選択不可・理由表示。正常メモは選択可。不正タグは除外し影響メモに事前警告。保存先の厳格検証は緩めない。
- 初期全件未選択、手動選択。1ページ50件、移動後も選択・件数保持。ページ単位一括選択／解除だけ提供し、不正行は除外。全頁一括選択・比較結果による自動選別なし。
- 重複メモIDだけでは不正にせず各行を表示・選択可。必要なら「同一データの可能性あり」等を表示する。元IDだけで選択を管理しない実装方式を設計する。
- 元IDを基準に変換前のファイルと現在データを比較し「新規／一致／差分あり」。タイトル・本文・タグID／名前／色・ピン／ゴミ箱状態・作成更新日時・revision等、定義した項目で比較。同IDタグの名前／色や日時だけの差も差分あり。異なる項目名だけ表示、前後値の差分不要。比較で選択可否を変えず、一致でも任意追加可。比較項目の最終列挙は実装設計で明記する。
- バックアップ原本は書換えない。保存先v2・pending・未知版・破損・読取不能は停止し、自動更新／復旧しない。

### 4.2 メモとタグの変換（決定済み）

| 属性 | ①追加型統合での値 |
|---|---|
| id | 全選択正常メモに新UUID。元ID・内容が一致しても追加可能、自動除外なし |
| title / body | バックアップ値 |
| createdAt / updatedAt | 復元実行時刻 |
| revision / lastRequestId | 1 / null |
| pinnedAt | ピンありなら復元時刻、なしならnull |
| deletedAt | ゴミ箱ならバックアップ日時をそのまま保持、通常ならnull |
| 関連 | 下記タグ対応表で再マップ |

タグは個別選択せず、選択メモが参照しなくても全正常タグを統合する。[オーナー決定](https://github.com/k-tsuichihara/MyHomePage/pull/19#issuecomment-6539978323)により、異ID同名を別タグ追加とする旧要件は撤回し、既存同名タグの再利用（A案）を採用する。再利用時は現在の名前・色を保持し、バックアップの色が異なっても別の同名タグを作らない。

| 条件 | 決定した対応 |
|---|---|
| 同ID・同名・同色 | 既存を再利用 |
| 同IDで名前か色が異なる | 同名の別既存タグがあれば再利用。なければ新UUIDで追加。ただし名前一意性を満たすこと |
| 異IDだが同名 | 既存同名タグを再利用し、追加メモの関連を付替え。現在の色を優先 |
| IDも名前も異なる | 新規タグ追加 |

既存タグ・他メモ関連は変更せず、現行tagKeyによる名前一意性・通常管理・検証器の制約を維持する。大小文字・正規化等の複合ケースの決定的な対応は次節の提案としてレビューする。

ファイル内の同値タグID複数定義は全定義を不正として除外。一つを選ばず、正常メモは当該参照だけ除外して復元可、事前警告する。②単件回復の「既存タグだけ参照」と混同しない。

### 4.3 既存v3との整合・具体設計案・保存安全性

- **履歴A案を決定**：現在のdeletedMemoIdsを原表記・順序ごとそのまま保持し、バックアップ履歴を取り込まない。和集合・衝突時の自動削除・間引きなし。現存行と履歴の非衝突、通常transactの履歴不変ガードを維持する。新UUIDは現存メモ・現在履歴・候補IDと大小文字同値で照合する。元IDを再利用しない。
- 利用者への説明と受入条件に「追加型統合ではバックアップ側の削除履歴自体は復元されない」を含める。ファイル原本の履歴は保全するが保存先へ転記しない。③初期復元にはこのルールを適用せず、具体仕様は保留。
- ファイル専用の段階検証・不正行診断を設け、保存検証器は緩めず変換後候補全体を厳格検証する。以下の具体案は未承認の提案として区別する。
- 選択正常メモ＋全正常タグを単一の整合的JSON書込にする。逐次saveでは原子性を満たさないため内部候補commit境界を設計する。事前表示された不正行除外と書込途中の部分成功は別。
- Web Locks内の最新値再読込・全体検証・書込直前照合・読戻し、容量不足・試行後例外・読戻し失敗のunknown、自動再送／ロールバック禁止、A案、旧キー・migration・legacySnapshot不変を維持する。

**複合ケースの決定的マッピング案（要レビュー、今回確定しない）**

1. 同値UUIDが複数定義された不正タグを先に全除外する。その後、名前比較は既存tagKey（ASCII A〜Zのみ折畳み、NFC等の追加正規化なし）で行う案。UUID比較はuuidKey、色は検証済み値の厳密比較とし、現在タグ優先は全ケースで維持する。
2. 現在タグからtagKey→タグの対応表を構築する。現在データが一意性違反なら保存先全体不正として停止。ファイルの各正常タグに対し同ID・同名色一致を再利用し、それ以外も同じtagKeyの現在タグがあればそのIDへ対応付ける。既存名表記・色を変更しない。
3. 現在に同じtagKeyがない複数ファイルタグは一つの新規タグへまとめる案。代表はuuidKey昇順、同値なら元表記順で決定（同値ID重複は既に除外済み）。代表の名前・色を採用し、新UUIDを発行して全元タグIDを対応付ける。配列順で色が変わらないようにする。ファイル内の色差を統合する効果は事前に表示する。これは代表選択を伴うため採否をレビューする。
4. 新規タグのIDは元IDを保持できる場合も既存方針に合わせた生成契約を実装設計で明記する。同ID差異時の新UUIDは確定済み。候補の名前一意性・関連整合性を最後に全体検証し、自動改名はしない。

複合例「同ID・同名・色だけ違う」では、同名の現在タグが当該ID自身である。ここで新UUID同名追加は一意性に反するため、上記案は一般方針の「同名既存再利用・現在色優先」を優先し同IDを再利用する。§4.2の「同ID差異なら別既存または新UUID」の字義との優先順位を明示した提案であり、この複合例を含め一括レビューする。無断で確定事項へ昇格させない。

**残る小論点への推奨案（要レビュー）**

- 重複メモID：不変ファイルの行位置で選択を識別し、元IDに紐付く妥当なタグ関連集合を各正常行で共通参照する案。選択行ごとに新メモIDへ付替える。元ファイルが行別の関連を表現できない限界を警告し、内容から推測しない。
- 不正関連：識別できるメモに付く不正タグ参照は除外・警告、存在しないメモへの関連は全体警告として非採用とする案。行の形や参照先を安全に解釈できない場合は全体中断する保守案。重複した有効ペアは事前通知の上で一つの候補関連へまとめる案。保存先の重複関連許可ではない。
- メモ未選択：実行ボタンを無効化し書込0件とする案。少なくとも1件選択時に参照されないものも含む全正常タグを統合する。タグ専用インポートを今回追加しない。これは採否をレビューし、決定済みの全タグ統合要件と区別する。

### 4.4 選択的な過去状態復元（完全削除後回復のみ一部確定）

これは①の衝突拒否を緩めるオプションではなく、独立した操作として扱う②である。現存メモへの過去状態適用は以下の未承認案、完全削除後の回復は§4.4.1の確定範囲を適用する。後者はボタン押下が明示操作であり、別確認ダイアログや編集ドラフトを要求しない。選択した操作全体を単一書込とし、実行時に失敗行だけを除外する部分成功は認めない。ただし後者の存在しないタグの非引継ぎは確定した規則であり、メモ本体の失敗とは扱わない。

| 方式案 | 利点 | リスク・推奨 |
|---|---|---|
| 同IDの現存メモへ選択フィールドを復元 | 誤編集を回復しつつ現在のID・参照を維持できる | **現存メモ向け第一候補**。現在revisionを基準に加算し、バックアップrevisionへ戻さない |
| 全フィールドを過去値へ置換 | 操作は単純 | 作成日時・revision・lastRequestIdや正常な追記を巻き戻すため採用非推奨 |
| 新IDで新しいメモとして直接保存 | 元メモID・削除履歴を保持して内容を回復できる | 完全削除後の単件回復として決定。読取専用プレビューから実行し、編集画面を経由しない（§4.4.1） |
| 完全削除済みの同IDを再使用 | 過去参照を維持できる | 履歴契約に反するため採用しない。履歴を削って通さない |

現存メモ向け推奨契約案：

- タイトル・本文・タグ選択・ゴミ箱状態を別の選択項目とする。既定で全項目を上書きせず、利用者が選んだ差分だけを固定する。選択外の現在フィールド・他メモ・タグ・関連は保持する。
- ID・createdAt・lastRequestId・ピン状態は現在値を保持する案。updatedAtは適用時刻、revisionは現在値+1とし、安全整数上限なら書込前拒否。過去revision・更新日時をそのまま適用しない。
- ゴミ箱から通常状態へ戻す場合は専用の明示選択を必須とし、deletedAt=nullとする案。過去のゴミ箱状態へ戻す操作は現在時刻での新しいゴミ箱移動として扱う案。pinnedAtは既存の状態操作契約に従って保持する。過去日時の再現とは区別し、日時方針も承認事項とする。
- タグ選択を復元する場合だけ当該メモの関連を置換する案。現存メモへの復元のタグ不足・衝突の具体方式は未承認であり、①のタグID再マップを無条件流用しない。②単件回復の既決タグ規則とも区別する。
- 対象ID・現在revision・対象の全項目・関連・履歴・新旧キー生値と選択差分を確認に束縛する。正常な追記も上書き範囲に入るため、実行前に差分を明示し、確認後の変更は全体拒否して再比較する。
- 現存メモへの過去状態適用の履歴方針も未承認。①の旧和集合案は根拠にせず、現在履歴保護と現存ID非衝突を守る。現在履歴にある元IDを再使用しない。

### 4.4.1 完全削除されたメモを新しいメモとして復元（今回確定）

今回のオーナー指示により、従来の「新ID未保存ドラフト・別確認・重複警告」の比較案を、以下の単件直接保存方式に置き換える。対象は完全削除されたメモの回復に限定する。その他の不在メモや現存メモの過去状態復元へ勝手に拡張しない。

**保存対象と非破壊性**

- バックアップ内の対象1件を新しいメモとして復元する。複数件の一括復元は対象外。
- 毎回新しいUUIDを発行し、元メモIDを再利用しない。元IDに対応するdeletedMemoIdsを変更・削除しない。
- 既存メモ、既存タグ、他メモのタグ関連を変更しない。今回の操作を①の全タグ統合へ流用せず、通常のトランザクションガード・排他制御も緩めない。

**画面と明示操作**

1. バックアップ内のメモ一覧から対象を選択する。
2. 既存のメモ詳細画面を流用した、読み取り専用のバックアッププレビューモードでタイトル・本文・タグ情報など必要な内容を表示する。
3. 編集・ピン留め・削除等の通常操作を使用不可とし、「新しいメモとして復元」ボタンを表示する。
4. ボタン押下で保存処理を直接実行する。編集画面を経由せず、通常時の追加確認ダイアログは表示しない。ボタン押下自体を、この単件回復の明示操作とする。
5. 復元前のプレビューの戻る操作ではバックアップ一覧へ戻る。作成成功確認後の遷移は下記の復元後UI方針に従う。確定的な拒否・失敗と結果不明を区別し、判定不能な結果を成功や未保存と断定しない。

**復元後UI（案Bを採用・決定済み）**

- 通常の保存成功時・再診断で作成確認できた時とも、新しく作成されたメモの通常の詳細画面へ自動遷移し、通常の閲覧・編集を可能にする。通知は「メモの作成を確認しました」とし、バックアップ内容との完全一致まで保証する表現を避ける。
- メモの作成確認と、復元された内容の利用者確認を分離する。毎回バックアップと実メモの比較を強制せず、比較専用画面をv1.1.0の必須要件にしない。
- 復元直後に限り、通常詳細画面に「バックアッププレビューに戻る」導線を表示する。復元元プレビューと新メモの関連は一時的な画面状態で保持し、ページ再読込・画面終了後まで永続保存しない。具体的な画面実装・状態寿命の細部は未決定。
- 作成成功を確認した後の詳細画面読込・遷移失敗はUIの失敗として分離し、確認済みの保存成功を失敗や結果不明へ書き換えない。

**復元する属性**

| 属性 | 確定した要求 |
|---|---|
| id | 新しいUUID。元IDは再利用しない |
| title / body | バックアップの値 |
| createdAt / updatedAt | 復元実行時の日時。バックアップ日時を引き継がない |
| pinnedAt | ピン留めなし |
| deletedAt | 通常メモ（ゴミ箱外） |
| revision | 1（既存の新規作成契約に準拠） |
| lastRequestId | null（既存の新規作成契約に準拠）。当該requestIdを永続記録しない |

バックアップ時点のピン留め・ゴミ箱状態・作成更新日時は引き継がない。

**タグは現在データを優先する**

- バックアップ内の対象メモのタグIDを確認し、現在データに同じIDが存在する場合だけ紐付ける。ID同値性は既存UUID比較契約に従う。
- 同IDの名称・色が変化している場合、現在の名称・色を使用する。同名でも異なるIDには紐付けない。
- 現在存在しないタグは作成・復活させず、紐付けない。ただしメモ本体は復元可能とする。既存タグマスタ・他メモの関連は変更しない。
- プレビューでは引き継げないタグがあることを知らせる。例：「バックアップに含まれるタグ『重要』は現在存在しないため、復元されません。」これは画面内のテキスト表示であり、ログやエラーへの実値出力は認めない。
- [タグ再検証の追加決定](https://github.com/k-tsuichihara/MyHomePage/pull/19#issuecomment-6538673874)により、プレビュー時と保存直前の「バックアップ内の対象メモのタグIDのうち、現在存在して紐付け可能なIDの集合」を比較する。UUIDは既存契約どおり大小文字同値として照合し、名前・色では対応付けない。
- 紐付け可能なID集合が変わった場合（対象タグの削除、同IDが再び存在するようになった場合等）は、書込前に保存を中止する。最新状態でプレビューを更新し、変更点を通知する。利用者が改めて「新しいメモとして復元」を操作した場合だけ保存へ進む。自動継続や追加確認ダイアログによる代行はしない。
- 対象タグの名前・色だけが変わり、紐付け可能なID集合が同じなら、その理由で保存を中止しない。保存後の表示は現在の名前・色を使用する。
- 対象と無関係なタグの変更は保存を妨げない。別IDで同名タグが作られても付け替えず、対象ID集合が変わらなければ保存を妨げない。
- 保存直前の再検証は既存の排他・整合性保護に従い、書込と競合しない保護区間内で実施する。画面側の事前チェックだけで済ませず、通常のトランザクションガードを緩めない。プレビュー時点から全体の生値が不変であることをこの単件回復の追加条件にして、上記の許容変更まで拒否しない。①追加型統合・③初期復元のスナップショット契約は変更しない。
- この書込前の明確な中止は、保存試行後のunknownと区別する。後者は自動再保存せず、以下の新UUIDによる再診断を適用する。プレビュー時の集合の保持・失効判定の具体APIや状態管理方式は未承認であり、今回確定しない。

**意図的な再復元と二重実行の区別**

- 同じバックアップ内のメモを何度でも復元可能とする。利用者が意図して再実行するたびに、新しいメモID・新しい保存要求を使用する。
- タイトル・本文等で重複判定しない。v1.1.0では重複警告も実装しない。警告は必要になった場合の将来検討事項とする。
- 保存中は復元ボタンを無効化し、同一操作の連打・非同期再入による二重実行を防止する。表示上の無効化だけでなく、同一操作を多重発行しない制御を既存の保存基盤と整合させる。
- メモIDはメモの識別、requestIdは保存試行の識別であり、役割を混同しない。既存A案を維持し、永続要求台帳・再送安全性を追加保証しない。
- 結果不明時は新ID・新requestIdの発行による自動再試行を禁止する。意図的な再復元の許可を結果不明要求の自動再実行許可と解釈しない。再診断は以下のとおり新メモUUIDを照合対象とし、requestIdを永続的な成功照合キーにはしない。

**新UUIDによる結果再診断（今回追加決定）**

[先生レビューの追加決定](https://github.com/k-tsuichihara/MyHomePage/pull/19#issuecomment-6538813440)に従い、保存試行前に発行した新メモUUIDを診断が終わるまで保持し、書込結果が不明になった場合は現在データを再読込して照合する。永続的な操作履歴・専用管理DBはv1.1.0で追加しない。revision=1・lastRequestId=null、requestIdの受付時予約・既存A案を維持する。

| 診断状態 | 判定・表示と操作制約 |
|---|---|
| 作成確認 | 当該操作で事前発行・一時保持した新UUIDのメモが現在存在し、現在の保存データ全体が構造・参照関係を含め妥当である。初回のrevision・日時・タイトル・本文・タグID集合との一致は要求しない |
| 未保存確定 | 書き込みに到達しなかったことが確実な場合に限る。必要な事前チェックを経た利用者の手動再操作を許可する |
| 結果不明 | 読取失敗、破損、判定不能、書込の可能性があるのに新UUIDが見つからない場合等。成功・未保存とは断定せず、自動再試行しない |

新UUIDの不在だけで未保存確定にしない。保存後の別タブ削除等の可能性が残る。同内容の別IDメモがあるだけでも成功にしない。利用者に判断材料を示すことは、自動再試行・自動補正・新ID再発行等の解禁を意味しない。タグID集合変化等の書込前の明確な中止は、書込試行後の結果不明と別に扱う。

この単件復元は、[成功判定・復元後UIの追加決定](https://github.com/k-tsuichihara/MyHomePage/pull/19#issuecomment-6539060818)と[3状態・再診断の確定](https://github.com/k-tsuichihara/MyHomePage/pull/19#issuecomment-6539214702)に従う。旧4状態の「要確認」は廃止し、作成確認・未保存確定・結果不明の3状態とする。**初回保存の生成契約と結果不明後の再診断条件を分離**する。初回は新UUID、revision=1、lastRequestId=null、新しい作成更新日時、タイトル・本文・復元可能タグ等の保存契約を厳格に満たす。再診断は通常の別タブ編集があり得るため、初回値への一致を要求せず、現在データ全体の妥当性と当該新UUIDの存在を確認する。UUIDだけで破損データを成功としない。

「作成確認」は現在のメモの存在と保存データの妥当性を確認した意味であり、元の書込との因果関係やバックアップ内容の完全一致を保証しない。永続receipt・冪等性の追加でもない。①追加型統合・③初期復元の厳密一致・unknown契約や既存保存APIの結果契約は変更しない。

ページ再読込・タブ終了等で一時保持情報を失う限界を明示し、診断対象をタイトル・本文検索等で推測しない。一時保持情報がなければ、この方式での成功確認・未保存確定を保証できない。万能な診断保証や再起動後の要求追跡を謳わない。

**再診断の実行・表示（決定済み）**

- 結果不明の検出直後にシステムが自動で1回だけ再診断する。待機時間を設けた自動再試行・定期ポーリングは行わない。再診断は読み取り専用で、書込・自動修復・再復元を一切行わない。
- 自動再診断でも不明なら、「保存状況を再確認」「もう一度復元する」「復元せずに戻る」を提示する。手動再確認は任意のタイミングで何度でも可能だが、同時実行・連打を防止する。
- 再診断中は「保存状況を確認しています…」を表示し、アプリ内の画面遷移・戻る・他操作を抑止し、終了後解除する。ブラウザ標準の更新・終了を完全には防げない。同期的なlocalStorage読取・JSON解析ではローディング表示が描画されない場合があることにも留意する。
- 作成確認なら通常詳細へ自動遷移し、依然不明なら結果不明画面に留まる。読取エラーと整合性エラーは原因表示を区別し、「再診断に失敗／復元結果は不明」と示す。例：「保存状況の再確認に失敗しました。メモが作成されたか確認できませんでした」。「復元そのものが失敗した」と誤表示しない。

**結果不明からの利用者による独立した再復元（決定済み）**

- 「もう一度復元する」は、不明な書込の自動リトライではなく、新UUID・新requestIdの独立した新規復元操作とする。この結果不明ケースに限り「既に作成されている可能性があり、同内容のメモが重複する場合がある」と説明する。通常時の意図的な繰り返し復元には内容重複警告を出さない。
- 新規操作でもプレビューからの条件、タグID集合、現在保存データ全体の妥当性等、既決の事前検証を改めて行う。破損・妥当性確認不能なら書込不可。利用者の選択を理由にガードを回避しない。
- 「復元せずに戻る」は保存データ・バックアップ・削除履歴を変更しない。識別用新UUID等はメモリ内で一時保持するだけとし、ページ再読込・タブ終了後の追跡や結果保証はしない。

一時保持の具体API／状態寿命の細部、個人情報を漏らさない画面実装等は引き続き実装設計で詰める。保存済みデータの自動修復は認めない。内容を表示する場合もテキスト表示・個人情報非露出ルールに従い、ログやエラーへ生値を出さない。

**既存契約との整合・訂正済み事項**

現行[local-memo-store.ts](../src/local-memo-store.ts)と[LOCAL-SAVE.md](LOCAL-SAVE.md)の新規作成はrevision=1・lastRequestId=null。[先生の訂正レビュー](https://github.com/k-tsuichihara/MyHomePage/pull/19#issuecomment-6538481939)により、以前の「当該requestIdを設定」という要求を訂正し、完全削除メモの新規復元も同じ値とすることを確定した。requestIdは保存試行の識別と受付時予約に使い、メモのlastRequestIdへの永続記録とは区別する。通常保存契約・コード・保存形式は変更せず、復元専用の例外保存経路も設けない。

今回未確定のまま残すもの：プレビュー時の対象タグID集合の保持・失効判定の具体API／状態管理方式、新UUID／復元元関連の一時保持方式と寿命詳細、決定済み分類・操作に従う画面の実装細部、その他の選択的復元、初期復元の安全条件・保存契約、JSON上限・厳格パーサー仕様。新UUID存在＋現在データ全体妥当性による作成確認、3状態分類、即時1回の自動再診断・任意回数の手動再診断、独立した手動再復元と限定的重複説明は決定済み。既存の他の提案を確定値に昇格させない。

### 4.5 保存領域喪失時の初期復元（具体仕様は保留）

以下は従来の比較案で、確定ではない。オーナー判断を待ち、①の変換を無条件適用しない。

| 現在の診断 | 推奨する入口・停止条件 |
|---|---|
| 新旧キーとも不存在 | 専用初期復元の候補。空であることは履歴喪失なしの証明ではない |
| v3が存在し空メモ、履歴あり／タグあり／全て空 | 既存データとして①②へ。空判定で置換しない |
| v2／pending／未知版 | 既存の形式更新・復旧手順へ案内し停止。復元で代行しない |
| 不正JSON・破損v3 | 不存在と区別し停止。利用者による保全と別途承認された救出手順が必要 |
| 読取例外 | 存在の有無を判定できないため停止。新規作成しない |
| 新キーなし・旧キー残存 | 旧データありとして停止。既存移行または別の保全判断が先。旧値を変更しない |

初期復元は通常の空データ初期化を経由しない。新旧キーの不存在、保存領域インスタンス、バックアップ不変値、世代を固定し、専用確認後に共通Web Locks内で再読込・不存在を再確認する案。途中でどちらかに値が現れたら拒否する。候補はバックアップ全メモ・タグ・関連・履歴を保持したversion=3、migration={status:'not-required'}とする案。これは旧移行の経緯を復元したという意味ではなく、新しい領域へのファイル導入を表すためのmetadataであり、既存metadataの上書きはしない。

候補全体検証後、一つのJSONを一回だけ書き、旧キー不存在と新キーの読戻し一致・妥当性を検証する。ローカル保存での単一キー書込であって、ディスク障害までの耐久性保証ではない。書込試行後の例外・容量不足・読戻し不一致はunknown、自動消去・元値書戻し・再試行なし。再診断で有効v3が観測されても過去の成功を認定せず、現在状態として扱う。古い初期復元確認は再利用しない。

確認画面には、保存領域全消失をアプリが証明できないこと、バックアップ後の削除履歴は失われており当時存在したメモが再導入され得ること、旧コピーの全消去とは別であることを明示する。必要なら複数バックアップの履歴を照合する工程を別承認する。失われた履歴を捏造して「復活なし」を保証しない。この保証限界を承知した初期回復の受入が必要。

### 4.6 3方式とバックアップ形式の互換性

backupVersion=1案は、全フィールド・関連・履歴を含むため、①の追加判定、②の過去内容比較、③の候補全体構築に必要なデータを持つ。選択方式・対象・現在revision・新規回復IDは適用プランの情報で、ファイルに権限や確認を持たせる必要はない。したがって**3方式で共通形式を使う案を推奨**する。ただし実装・受入テスト前の設計上の評価である。

exportedAtだけではバックアップ時点後の変更・削除や出所を証明できない。将来、回復元の永続識別・暗号化・署名・領域履歴を必須にする場合は、厳格な未知項目拒否と整合する新backupVersionを定義し、旧ファイルの保証範囲を明示する。未知metadataの黙認、v1への必須項目後付け、任意backupIdを出所証明に使うことはしない。旧キー／migration除外と平文告知は3方式で共通とする。

## 5. プレビュー・明示確認・状態遷移

### バックアップ作成

`idle → reading → prepared → save-started / cancelled / failed`

取得時刻・通常／ゴミ箱／タグ／関連／履歴の件数、暗号化なし、除外範囲を表示する。preparedとファイル保存成功を混同しない。非同期応答には操作ID・保存先インスタンス・画面セッションを照合する。

### 追加型復元

`idle → file-selected → validating → reading-current → preview-ready / conflicts / rejected`

`preview-ready → confirmation → applying → applied / rejected / unknown`

`unknown → explicit-reinspect → current-observed → fresh-preview → fresh-confirmation`

- ファイル選択・解析・プレビュー・取消は書込0件。ファイル変更、再プレビュー、現在値再取得、対象保存先／画面セッション変更、取消で古い確認を失効させる。
- プレビューでは選択・比較・不正行の件数、タグ除外警告、通常／ゴミ箱内訳、履歴方針の影響、現在行を消さない方式であること、部分適用なし、必要な保存容量の見積りを示す。
- 初期表示は件数中心とし、本文を自動的に全件表示しない。必要な詳細だけ利用者操作でエスケープして表示する。ファイルや本文をURLへ載せない。
- 解析したバックアップと候補、承認時の新旧キー生スナップショットを独立した不変値としてメモリ保持する。後続のファイル差替えや呼出側オブジェクトの変更を反映させない。
- 確認は操作種別・保存先インスタンス・プレビュー世代・元スナップショット・候補に結び付け、一回だけ消費する。requestIdは承認の証明に使わない。
- 未保存ドラフト、未解決の保存要求、実行中の書込がある場合は、既存の保護契約に従う。初版は編集・保存先切替を抑止し、ドラフトを黙って捨てて復元へ進まない案とする。
- 確認画面・ファイル選択ダイアログの間はWeb Locksを保持しない。適用直前に取得し、現在状態の再検証と生値一致を確認する。不一致なら自動再計画せず、未書込拒否して再プレビュー・再承認を要求する。
- 保存成功後の一覧再読込失敗を、復元失敗／結果不明に書き換えない。逆に書込結果不明を、一覧が似ているだけで成功へ昇格させない。完全削除メモの単件復元は§4.4.1の3状態分類と読み取り専用再診断を適用する。作成確認後の通常詳細画面への読込・遷移失敗も、書込結果とは分離する。

## 6. API境界案と既存コードへの影響

以下は将来実装する責務の案であり、今回APIを追加していない。

| 層／API案 | 責務 | 禁止事項 |
|---|---|---|
| ファイルアダプター | Fileサイズ確認、厳格UTF-8読取、Blob生成、利用者操作による保存開始 | localStorage直接操作、任意パスへの自動保存、ファイル名をパスとして使用 |
| parse/validateBackup | 全体形式・上限・行別診断。正常／不正行・タグ警告を独立した値で返す。出力候補は厳格検証 | 保存先アクセス、v2自動変換、実値付きエラー、不正保存先の救済 |
| planLocalRestore | 検証済み現在v3とファイルから差分・衝突・候補を純粋に計画 | 書込、現在値優先／ファイル優先の暗黙選択、部分適用 |
| prepareLocalExport | 共通ロックで検証済みv3を取得、専用ファイルへ射影して再検証 | 保存形式更新、OS保存完了の断定 |
| 復元controller | 非公開プラン・世代・確認・非同期応答・ドラフト保護を管理 | UIへストア・生スナップショット・任意commit能力を公開 |
| applyLocalRestore（内部ポート案） | 同じストア寿命のrequestId予約、ロック内の現在値再検証、固定プランとの照合、単一書込・読戻し | 通常transactガードの緩和、deleteTrashの流用、履歴削除、旧キー書込 |

現行の通常transactは履歴不変、deleteTrashは検証済み削除対象だけ履歴追加可能である。複数行追加の単一候補を単件saveの逐次呼出では保存できないため、**新しい専用書込経路の追加設計・承認が必要**。共通のI/Oカーネルを使う場合も、復元経路では現在の全行・関連の保持、既存履歴の保持、migration不変、候補全体妥当性を検証する。無制限の候補JSON上書きAPIを作らない。

PR #18と同様、controllerでの利用者確認と低レベルポートの入力検証は別の保証である。初版の推奨は、プランをprivateな対応表で保存先・世代へ束縛し、UIは不透明なプランID／確認トークンだけを扱う構成。低レベルポート自体で何を強制するかは実装前に明文化し、任意のtrueやファイル内requestIdで承認扱いにしない。

requestId A案の共有集合を維持し、UUIDとして有効な試行IDは内部適用ポート受付時に他の検証・awaitより前に予約する。拒否・unknown・no-changeでも戻さない。初期ファイル検証／プレビューは書込要求ではなく、別の操作IDで管理する。別ストアを作り直して使用済み集合を消さない。

3方式はplanの判別子と内部適用ポートを分ける案とする。①は全選択メモ新UUID追加・既存行不変と§4.3の現在履歴のみ保持、②の現存メモ向けは選択対象のrevision加算と選択外不変、③は新旧キー不存在をそれぞれ強制する。①のプランを②③へ流用せず、既存commitの「空ならv2を生成」という挙動へ③を接続しない。②の完全削除後回復は§4.4.1の直接新規保存であり、編集ドラフトを作らない。既存のドラフト保護を維持し、復元用の無検証書込経路を作らない。

3方式とも診断・方式選択・方式別プレビューを経るが、確認内容と候補生成は共用しない。①③と②の現存メモ向けは明示確認後の適用案を維持する。②の完全削除後回復は§4.4.1のボタン押下から直接保存し、通常時の追加ダイアログを設けない。方式変更は以前の操作対象を流用しない。②の現存メモ向けでは選択差分と上書きされる現在値、③では履歴喪失の限界を追加提示する。未保存ドラフトの退避を暗黙実行せず、保存・破棄・取消の既存確認を経る。既存controllerとの接続詳細は未決で、古い応答で画面を上書きしない。

## 7. 失敗・容量不足・結果不明

| 発生点 | 状態・対処 |
|---|---|
| ファイル読取・検証・現在値取得失敗 | rejected/failed。書込0件。現在データを空扱いしない |
| 衝突・確認失効・保存先変化・ロック非対応 | rejected。書込0件。新しいプレビューから再確認 |
| setItem前の拒否 | 現在値不変。部分候補を書かない |
| setItem試行後の例外・容量不足・読戻し失敗／不一致 | unknown。成功・未実行と断定しない。自動再送・旧値書戻し・初期化なし |
| 読戻し一致・候補再検証成功 | applied。その後の取得失敗は別状態 |
| unknown後の再取得が候補と一致 | 現在値一致を表示するだけ。要求の過去成功とは判定しない |
| unknown後の再取得が元値と一致 | 未実行の証明ではない。新プレビュー・新確認・別requestIdでのみ再操作 |
| unknown後の取得失敗・破損・pending | 停止継続。自動修復・旧ファイル再適用をしない |

上表の再取得による成功認定をしない規則は①追加型統合・③初期復元の案を維持する。②の完全削除後単件復元は§4.4.1に従い、新UUID存在＋現在の保存データ全体の構造・参照関係の妥当性で作成確認する。初回保存値との一致は要求しない。不在だけで未保存確定とせず、結果不明の自動再保存・修復・ロールバックは禁止する。直後1回の自動再診断は読取のみであり、自動再保存とは別である。

適用は一つのJSONにまとめる。大きいファイルを複数回の部分書込に分けない。容量見積りは成功保証ではなく、実際のQuotaExceededErrorを処理する。容量不足で履歴・メモ・旧キー・snapshotを削除して空きを作らない。

事前バックアップの作成は推奨するが、作成済みファイルを自動ロールバック用に上書き復元しない。書込結果不明時に元のファイルを戻すと、他タブ更新や完全削除履歴を巻き戻す危険がある。

## 8. 外部ファイルと個人情報の保護

### 入力量の上限案（数値は未承認）

| 対象 | 初期候補 | 適用方法・限界 |
|---|---:|---|
| 入力ファイル | 10 MiB（10×1024×1024 bytes） | File.sizeで全読取前に検査。復号・展開機能は初版なし |
| メモ | 10,000件（通常＋ゴミ箱） | 個別文字数制約も併用 |
| タグ | 5,000件 | 名前一意性と関連整合性も検査 |
| 関連 | 100,000件 | 同値重複・孤立関連を拒否 |
| 削除済みID | 100,000件 | 超過時は拒否。既存履歴を間引かない |
| JSON最大ネスト | 32階層 | 型検証より前の解析予算として強制する方式を選定 |
| 統合後候補JSON | UTF-8で16 MiB | ファイル上限とは別。現在データとの合計が上限を超えれば全体拒否 |

これらは同時に満たす必要があり、最大件数まで本文を埋め込める保証ではない。UTF-8バイト数、JS文字列長、localStorageの容量計算は区別する。実機・モバイルの時間／メモリ・実容量検証後に数値を承認する。既存データが上限を超える場合の救出用エクスポートも未決で、勝手に切り詰めない。

### 解析・表示・ファイル名

- 拡張子やMIMEだけで信頼しない。初版は`.json`を対象にし、MIMEは参考情報、最終判定はサイズ・文字コード・専用形式・内容検証で行う案。名前が適切でも不正内容なら拒否する。
- 入力ファイル名は保存キー・パス・HTML・URLへ流用しない。制御文字、パス区切り、双方向表示制御などの扱いを決め、表示は制限したプレーンテキストにする。出力名はアプリ生成の固定prefix＋安全なUTC日時＋`.json`とし、メモタイトルを使わない。
- UTF-8を厳格に復号し、不正バイトを置換文字で救済しない。BOM・別文字コードの許容範囲は形式仕様で固定する（初版はBOMなしを推奨）。
- 現行JSON.parseは同名キーの重複を検出できず、最後の値が残る。外部バックアップでは同名JSONキーも拒否する案とし、深度・入力予算と合わせた解析方式を別途選定する。正規表現だけでJSON構文を検査しない。新パーサ依存を追加する場合は事前承認が必要。
- 解析結果は全階層で許可キーだけを受理し、`__proto__`・`constructor`・`prototype`等を未知項目として拒否する。任意キーの再帰マージ、Object.assignによる未検証値の反映、evalをしない。検証器で明示的に再構築し、Map/Set等でUUIDを照合する。
- タイトル・本文・タグ名はテキストとして表示し、innerHTML・属性・スタイル・リンク先へ展開しない。バックアップ内に外部資産URLを持つ形式を採用せず、外部通信を行わない。
- 元JSON・本文・タグ名・ファイル名・旧キー・legacySnapshot・元例外メッセージをログ／分析送信／PR／テスト成果物へ出さない。エラーは固定コードと必要最小限の構造的な位置情報だけとする。
- 生ファイル、候補、承認材料はタブ内メモリだけ。ドラフト保護とは分けて、取消・終了時に不要な参照を解放しBlob URLもrevokeする。メモリの完全消去やOSスワップ等の消去は保証しない。
- 出力ファイルは本文・タグ・削除IDを含む平文の個人情報で、削除後もファイルやクラウド同期フォルダーに残り得る。共有・保存場所・利用者自身の管理責任を保存開始前に案内する。Gitへ登録しない。

### 暗号化

初版はアプリ内暗号化を対象外とする案。平文であることを明示し、利用者の明示保存以外で外部送信しない。暗号化を必要条件とするかはオーナー判断。将来実装する場合は暗号方式・鍵導出・パスワード忘失・認証付き暗号・復号前後のサイズ制限・相互運用を別設計とし、独自暗号や単なるBase64を暗号化と表示しない。

### 解析方式の比較と実測計画

| 候補 | 重複キー／深度の扱い | 依存・判断 |
|---|---|---|
| JSON.parse単独／reviver | 重複キーが既に失われるため不適合。深度の事後確認だけでは解析予算にならない | 依存不要だが単独採用しない |
| 制限付きトークン走査＋JSON.parse | 文字列のescapeを正しく復号し、オブジェクトごとのキー集合・ネスト深度・トークン予算を解析前に検査する。`a`と`\u0061`も同名拒否 | 新依存なし。独自走査器の構文境界・計算量の監査負担が大きい |
| 重複キー検出／深度制限可能な既存パーサ | オブジェクト終端までキー情報を保持し、深度・入力予算を超えたら途中停止できるAPIが必要 | **選定調査の第一候補**。保守状況・ライセンス・ブラウザ対応・依存規模を確認し追加承認。具体パッケージは未選定 |

候補は名前だけで採用せず、重複キー、escape同値、深い配列、巨大文字列、不正Unicode、構文エラーで比較試験する。将来の合成データ検証では上限の直下／一致／直上、低性能PC・モバイル相当と実機で、復号・解析・検証・差分・候補生成・直列化の所要時間とピークメモリ、UI応答性を別々に測る。中断要求の応答、Worker利用の要否、制限超過前に巨大展開しないことも確認する。数値目標・対応実機・パーサと上限の採用は計測計画レビュー後に承認し、10MiB／16MiB等を検証済み値としない。今回パッケージ追加・性能試験は行っていない。

## 9. 履歴保護の保証範囲とロールバック

- 保持できる履歴は、現在領域とファイルに残る情報まで（①は現在履歴のみ保持し外部履歴を取り込まない）。サイトデータ消去・全領域喪失・履歴欠落ファイルへの手編集で失われた情報を推測して再生できない。
- 空のv3が「初めての利用」か「履歴消失後」かは現行形式だけでは証明できない。初期復元の完成は要件だが、残存履歴を確認できる同一領域への統合とは保証範囲が違う。別端末／別ブラウザへの適用条件と、喪失後の限界告知を含む具体契約を別途承認する。
- バックアップの作成日時・sourceStorageVersionを出所証明にしない。任意ファイルをv3更新の導入元許可へ転用しない。
- 復元後もv3と履歴を理解する書込停止保守版を公開前の必須条件とする。旧v2コードへ戻してもデータはv3のまま停止し、自動逆変換しない。コード復帰とデータ復旧を分離する。
- 旧JSは旧キーへ書ける。復元で旧値へ同期・逆変換せず、既存の新旧分岐／旧タブ停止問題を解消済みとしない。
- 共通Web Locksに従わない同一originコード、最終照合後の外部書込、ABA、電源断・ディスク障害までを原子的に防ぐ保証ではない。

## 11. 決定事項とオーナー判断が必要な残課題

①のメモ全新UUID・手動選択／50件ページ・変換・タグ対応規則は§4に決定として記録した。②完全削除後単件回復の既決事項は維持する。①③への単件再診断規則の流用はしない。

オーナーの仕様判断が必要な残課題：
1. ③空保存先の初期復元の具体保存契約、他の現存メモ過去状態復元の仕様。
2. ファイル内同名タグの代表名・色を決定的に選ぶ案、重複メモIDの関連共通参照案、不正関連分類・未選択時書込0件案（§4.3）をまとめてレビューすること。
3. JSON版・段階検証境界、サイズ／件数／深度上限、パーサー依存、平文／暗号化の最終採用。

同名既存タグの再利用・現在色優先・名前一意性維持、および①の現在履歴のみ保持・外部履歴非統合は決定済みであり、再承認待ちにはしない。

行識別・一時保持・失効管理・候補生成API・画面細部は実装設計案として整理し、上記判断と分離する。今回は通常保存・完全削除・移行・復旧・保存形式・正式仕様を変更していない。

### 物理削除の最新方針と影響

ローカル版と将来のSupabase版でアプリからの物理削除を許可する。ただしゴミ箱内だけを対象とし、実行時の状態再確認と利用者の明示確認が必須。通常一覧からの直接完全削除・一定期間後の自動物理削除は実装しない。

ローカルのPR #18契約は既にこの方向で、メモ・関連除去と削除ID追加を単一書込する。物理削除許可はdeletedMemoIds削除や旧キー／legacySnapshotを含む全コピー消去の許可ではない。②単件回復も不要とはしない。新IDによる明示回復と元ID再利用防止を両立させる。

将来Supabaseでは本人所有行だけのDELETE権限制御・RLS等が必要。現行SQL/RPCの所有者照合・要求台帳・ID registryとの整合を実装前に設計する。直接DELETEの追加や既存GRANT変更をこの文書から許可されたと解釈しない。本PRでDB変更・接続は行わない。

## 12. 実装PRの分割案と完了条件

設計承認後、関連性を保って次の3単位を推奨する。PR番号は将来の採番に従う。

1. **バックアップ形式・出力・読取専用復元プレビュー**：純粋な検証・計画、承認済みパーサ／上限、File/Blob境界、合成メモリの隔離UI・ダウンロード試験。適用書込は提供しない。形式・全衝突規則・個人情報非露出をレビューできる状態を完了条件とする。
2. **承認付き追加型復元・競合／障害検証**：専用commit、privateプラン／確認、A案共有、結果不明時の再診断、所有環境の実Web Locks・複数タブ・容量・読戻し・保守停止。全必須テストと既存回帰を通し、未検証事項を引き継ぐ。
3. **選択的な過去状態復元・初期復元**：承認された②③の専用プラン・差分確認・適用境界を実装。誤編集・論理削除・完全削除後の回復、全領域喪失からの回復を別々の受入シナリオとし、タグ・revision・履歴・喪失限界・競合・unknown・容量・ドラフト保護を検証する。規模がレビュー困難なら②③を分割するが、片方を将来課題として完成扱いしない。

無制限の完全置換、暗号化、v2救出、バックアップの世代管理、別領域管理、クラウド連携は別判断とする。②の完全削除後回復は§4.4.1の範囲で設計決定したが、①とはタグ・対象・再診断が異なり、実装承認ではない。公開資産・実ユーザーデータに触れず、Draftレビュー・人間の受入・公開承認を分離する。

v1.1.0のバックアップ／復元完了ゲートは、3方式の契約承認、必須試験・実機性能検証、誤編集／誤削除および全保存領域喪失の人間による受入、未検証事項の公開可否判断である。段階1・2のマージやPASSだけでは完成としない。
