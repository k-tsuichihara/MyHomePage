## 2. バックアップ作成の対象と形式案

### 2.1 推奨範囲

初版は**通常利用可能なローカルv3全体のデータバックアップ**だけを対象とする。

- 通常メモ、ゴミ箱メモ、全タグ、全関連、削除済みID履歴を含める。検索・選択タグ・表示ページで範囲を減らさない。
- メモの全フィールド（日時、revision、pinnedAt、deletedAt、lastRequestIdを含む）を原値で保持する。lastRequestIdの保存は冪等性保証ではない。
- 旧キー、migration/legacySnapshot、未保存ドラフト、未解決要求内容、requestId使用済み集合、UI条件、認証情報は含めない。
- 旧キー・legacySnapshotを除外するのは、過去内容の不要な複製と別保存先への移行metadata混入を避けるため。この形式は保存領域のバイト単位の完全イメージではなく、旧データ移行の復旧資料にもならない。除外範囲を利用者へ事前表示する。
- v2・pending・未知版・破損・読取不能は作成を停止。空の履歴を補ってエクスポートしない。v2向け救出用アーカイブを将来設ける場合も別形式・別承認とし、復元可能と表示しない。
- v3でmemosが0件でも、タグや履歴を含む有効なバックアップとなる。全件数0と読み取り失敗は区別する。

### 2.2 専用ファイル形式（案）

UTF-8（BOMなし）のJSON。保存領域のversionとファイル形式のbackupVersionを独立させる。以下は合成の空データ例で、実行証跡ではない。

```json
{
  "format": "myhomepage.memo.local-backup",
  "backupVersion": 1,
  "sourceStorageVersion": 3,
  "exportedAt": "2026-01-01T00:00:00Z",
  "data": {
    "memos": [],
    "tags": [],
    "memoTags": [],
    "deletedMemoIds": []
  }
}
```

全階層の許可フィールドを固定し、未知／欠落項目・未知版・型違いを拒否する。生のv1配列、v2/v3保存JSON、形式識別子だけ書き換えたファイルは専用形式として受理しない。dataの検証には既存のメモ・タグ・関連・履歴規則を再利用し、偽のmigration=not-requiredを作って保存先の経緯を表現しない。

format/sourceStorageVersion/exportedAtはファイル内の自己申告であり、出所・所有者・真正性の証明ではない。日時が新しいことを優先上書きの根拠にしない。初版で署名・暗号化・真正性保証は提供しない。JSON検証は構造・整合性の確認であり、改ざん検出の保証ではない。

### 2.3 作成時の整合性

1. 明示エクスポート操作後、共通ロック内で保存先を読み、v3全体を検証する。読取だけで書込はしない。
2. 新旧キーを再確認し、整合した不変スナップショットをメモリへ確保する。現行loadは独立した値を返すが生値を公開しないため、必要な読取専用境界は実装時に設計する。
3. ロックを解放して専用JSONを生成し、同じファイル用検証器で再検証する。実際に生成したBlobのUTF-8内容・サイズも確認する。
4. 利用者操作でファイル保存を開始する。OSの保存ダイアログ中はロックを保持しない。

保証は取得時点のスナップショットで、ダウンロード完了時の最新状態ではない。ブラウザが保存開始したことと、利用者のディスクへ確実に保存できたことを区別する。失敗・取消時に「バックアップ保存済み」と断定しない。

## 3. 復元方式の比較

| 方式 | データ保護・履歴との関係 | 複雑さとリスク | 初版の推奨 |
|---|---|---|---|
| 完全置換 | バックアップにない現メモ・タグが消える。履歴まで置換すると巻戻し・復活を起こす | 履歴だけ和集合にしても内容欠落と衝突処理が残る。古いファイルの利用ほど危険 | 採用しない。将来も独立した破壊操作として別設計・承認 |
| 追加型統合 | 現在の行を消去・変更せず、新規IDの行と履歴だけを加える | 同じIDの内容差・タグ名衝突・履歴衝突を全体拒否するため、復元できないファイルがある | **第一候補**。衝突時停止を優先 |
| 上書き型統合 | 同じIDの内容や状態を更新できる | revision・日時を巻き戻す危険。どちらの内容を残すか、復活・タグ関連変更の追加判断が必要 | 初版対象外 |
| 新IDを発行するインポート | 現在のIDとは分離できる | 完全削除した本文を新IDで戻す迂回、重複登録、再インポート検出が問題になる | 通常復元として採用しない。別機能でも履歴保護との意味を要承認 |
| 読取専用プレビュー／検証のみ | 保存先を変更せず内容と衝突を確認できる | データ回復自体はできない | 安全な先行工程・失敗時の停止先として採用候補 |
| 未使用の別保存領域への復元 | 現在領域との衝突を分離できる可能性 | 新しい領域管理・切替・履歴の適用範囲・失われた履歴の扱いが必要 | 将来案。別キーへの自動フォールバックはしない |

「古い状態へ戻す」ことと「失われた行を追加する」ことは異なる。推奨する初版は後者であり、古い内容で同じIDを更新する機能ではない。画面の名称も「追加型復元」等でこの制限を明示する案とする。

## 4. 推奨する追加型統合の規則（要承認）

### 4.1 保存先とファイルの前提

- 保存先は既存の検証済みv3（completeまたはnot-required）に限定する。旧データのみ、キーなし、v2、v2/v3 pending、未知・破損・取得失敗は停止する。空のv3へ追加することと、保存領域消失後の初期設定は別問題。
- 移行・復旧・v3更新を復元処理の内部で代行しない。必要な処理は既存の承認手順で別途完了させる。
- バックアップは専用形式backupVersion=1/sourceStorageVersion=3のみ。v2ファイルや履歴のない古い形式を、自動的に空履歴として解釈しない。
- 形式が対応する古いファイルは、作成日時だけで拒否／優先せず、現在状態との全体照合で判断する。現在状態の巻戻しはしない。

### 4.2 削除済みIDと現存メモの衝突表

ここで「現存」はゴミ箱内も含む。UUIDは比較時だけ大小文字同値とする。Cは現在、Bはバックアップ、Dは削除済みID集合、MはメモID集合。

| 条件 | 推奨動作 | 理由 |
|---|---|---|
| B.M ∩ C.D が非空 | 全体拒否 | 現在完全削除済みのメモをバックアップから復活させない |
| C.M ∩ B.D が非空 | 全体拒否 | 外部ファイルの履歴を根拠に現在のメモを黙って消さず、履歴も無視しない |
| B.M ∩ B.D、C.M ∩ C.D が非空 | 入力／保存先の不正として全体拒否 | 一つのデータ内部で現存と完全削除は両立しない |
| C.DとB.Dで同値IDが重なる | 定義された和集合で一回だけ保持 | 独立して妥当な2履歴間の重なりは想定内 |
| 単一入力のD内に同値重複 | 不正として全体拒否 | 重複排除して不正ファイルを救済しない |
| 削除IDとタグIDだけが同じ | その理由だけでは拒否しない | 既存のメモ／タグ別名前空間を維持 |

候補履歴は **C.D ∪ B.D**。現在の履歴を原表記・原順序のまま先頭に保持し、バックアップにしかないIDをその原順序・原表記で追加する。大小文字を保存時に書き換えない。両方向の衝突があれば、対象を黙って除外する／ゴミ箱へ変える／新IDを発行する／現在メモを削除する等の回避はしない。

履歴は通常復元で削除・期限切れ・間引きをしない。履歴を取り込むこと自体も今後のID利用を制限するため、追加・重複件数とその効果をプレビューへ表示する。外部ファイルの履歴は実際の削除操作の真正性を証明しない。

### 4.3 メモ・タグ・関連の統合

1. 現在の全メモ・タグ・関連を保持する。バックアップにないことを削除や完全削除の証拠にしない。
2. 現在にないメモIDは、履歴衝突がなければ原内容・全メタデータのまま追加する。deletedAtも保持し、ゴミ箱メモを通常メモへ変換しない。新ID発行・日時更新・revisionリセットはしない。
3. 同値のメモIDが既に存在する場合は、全フィールドとそのタグID集合が一致するときだけ「同一行・追加不要」とする。内容・revision・状態・関連が違えば全体拒否。更新日時の新旧で優先しない。
4. UUID型フィールドは同値比較、文字列・日時の原表現・revision等は厳密比較する。同じ瞬間でも日時表記が異なれば、初版は保守的に衝突とする。オブジェクトキー順・関連配列順だけで衝突にしない。
5. タグも同じIDの全フィールド一致だけを同一行とする。異なるIDでタグ名一意キー（ASCII A〜Zのみ折畳み）が衝突した場合、再命名・ID付替え・自動統合をせず全体拒否する。
6. 既存行のUUID表記は現在のものを保持する。新しい行のUUID表記はバックアップのものを保持する。関連は同値ペアで照合し、既存ペアを保持して新しいペアだけを追加する。単一入力内の重複／孤立関連は事前拒否する。
7. 既存配列を先頭に保ち、新規行をバックアップ順で追加する。タグ使用件数は候補データから再計算する。一覧条件やピン順の契約は既存検索処理を使い、配列順だけに依存させない。
8. 保存先version=3と**保存先のmigrationメタデータをそのまま保持**する。バックアップ側から旧キー・legacySnapshot・migrationを取り込まない。

衝突はファイル全体の適用拒否とし、「復元可能な行だけ」の部分適用は初版で提供しない。同一行の判定と履歴の和集合は上記の明示的統合規則であり、不正入力の補正ではない。変更が全くない場合も診断結果を明示し、適用時に最新状態を再検証した上で未書込のno-changeを返す案とする。

## 5. プレビュー・明示確認・状態遷移

### バックアップ作成

`idle → reading → prepared → save-started / cancelled / failed`

取得時刻・通常／ゴミ箱／タグ／関連／履歴の件数、暗号化なし、除外範囲を表示する。preparedとファイル保存成功を混同しない。非同期応答には操作ID・保存先インスタンス・画面セッションを照合する。

### 追加型復元

`idle → file-selected → validating → reading-current → preview-ready / conflicts / rejected`

`preview-ready → confirmation → applying → applied / rejected / unknown`

`unknown → explicit-reinspect → current-observed → fresh-preview → fresh-confirmation`

- ファイル選択・解析・プレビュー・取消は書込0件。ファイル変更、再プレビュー、現在値再取得、対象保存先／画面セッション変更、取消で古い確認を失効させる。
- プレビューでは現在／追加／同一／衝突の件数、通常・ゴミ箱の内訳、履歴追加数、現在行を消さない方式であること、部分適用なし、必要な保存容量の見積りを示す。
- 初期表示は件数中心とし、本文を自動的に全件表示しない。必要な詳細だけ利用者操作でエスケープして表示する。ファイルや本文をURLへ載せない。
- 解析したバックアップと候補、承認時の新旧キー生スナップショットを独立した不変値としてメモリ保持する。後続のファイル差替えや呼出側オブジェクトの変更を反映させない。
- 確認は操作種別・保存先インスタンス・プレビュー世代・元スナップショット・候補に結び付け、一回だけ消費する。requestIdは承認の証明に使わない。
- 未保存ドラフト、未解決の保存要求、実行中の書込がある場合は、既存の保護契約に従う。初版は編集・保存先切替を抑止し、ドラフトを黙って捨てて復元へ進まない案とする。
- 確認画面・ファイル選択ダイアログの間はWeb Locksを保持しない。適用直前に取得し、現在状態の再検証と生値一致を確認する。不一致なら自動再計画せず、未書込拒否して再プレビュー・再承認を要求する。
- 保存成功後の一覧再読込失敗を、復元失敗／結果不明に書き換えない。逆に書込結果不明を、一覧が似ているだけで成功へ昇格させない。

## 6. API境界案と既存コードへの影響

以下は将来実装する責務の案であり、今回APIを追加していない。

| 層／API案 | 責務 | 禁止事項 |
|---|---|---|
| ファイルアダプター | Fileサイズ確認、厳格UTF-8読取、Blob生成、利用者操作による保存開始 | localStorage直接操作、任意パスへの自動保存、ファイル名をパスとして使用 |
| parse/validateBackup | 専用形式・上限・全フィールド・内部整合性検証。不変の検証済み値を返す | 保存先アクセス、v2自動変換、実値付きエラー |
| planLocalRestore | 検証済み現在v3とファイルから差分・衝突・候補を純粋に計画 | 書込、現在値優先／ファイル優先の暗黙選択、部分適用 |
| prepareLocalExport | 共通ロックで検証済みv3を取得、専用ファイルへ射影して再検証 | 保存形式更新、OS保存完了の断定 |
| 復元controller | 非公開プラン・世代・確認・非同期応答・ドラフト保護を管理 | UIへストア・生スナップショット・任意commit能力を公開 |
| applyLocalRestore（内部ポート案） | 同じストア寿命のrequestId予約、ロック内の現在値再検証、固定プランとの照合、単一書込・読戻し | 通常transactガードの緩和、deleteTrashの流用、履歴削除、旧キー書込 |

現行の通常transactは履歴不変、deleteTrashは検証済み削除対象だけ履歴追加可能である。復元の和集合はどちらにも該当しないため、**新しい専用書込経路の追加設計・承認が必要**。共通のI/Oカーネルを使う場合も、復元経路では現在の全行・関連の保持、既存履歴の保持、migration不変、候補全体妥当性を検証する。無制限の候補JSON上書きAPIを作らない。

PR #18と同様、controllerでの利用者確認と低レベルポートの入力検証は別の保証である。初版の推奨は、プランをprivateな対応表で保存先・世代へ束縛し、UIは不透明なプランID／確認トークンだけを扱う構成。低レベルポート自体で何を強制するかは実装前に明文化し、任意のtrueやファイル内requestIdで承認扱いにしない。

requestId A案の共有集合を維持し、UUIDとして有効な試行IDは内部適用ポート受付時に他の検証・awaitより前に予約する。拒否・unknown・no-changeでも戻さない。初期ファイル検証／プレビューは書込要求ではなく、別の操作IDで管理する。別ストアを作り直して使用済み集合を消さない。

## 7. 失敗・容量不足・結果不明

| 発生点 | 状態・対処 |
|---|---|
| ファイル読取・検証・現在値取得失敗 | rejected/failed。書込0件。現在データを空扱いしない |
| 衝突・確認失効・保存先変化・ロック非対応 | rejected。書込0件。新しいプレビューから再確認 |
| setItem前の拒否 | 現在値不変。部分候補を書かない |
| setItem試行後の例外・容量不足・読戻し失敗／不一致 | unknown。成功・未実行と断定しない。自動再送・旧値書戻し・初期化なし |
| 読戻し一致・候補再検証成功 | applied。その後の取得失敗は別状態 |
| unknown後の再取得が候補と一致 | 現在値一致を表示するだけ。要求の過去成功とは判定しない |
| unknown後の再取得が元値と一致 | 未実行の証明ではない。新プレビュー・新確認・別requestIdでのみ再操作 |
| unknown後の取得失敗・破損・pending | 停止継続。自動修復・旧ファイル再適用をしない |

適用は一つのJSONにまとめる。大きいファイルを複数回の部分書込に分けない。容量見積りは成功保証ではなく、実際のQuotaExceededErrorを処理する。容量不足で履歴・メモ・旧キー・snapshotを削除して空きを作らない。

事前バックアップの作成は推奨するが、作成済みファイルを自動ロールバック用に上書き復元しない。書込結果不明時に元のファイルを戻すと、他タブ更新や完全削除履歴を巻き戻す危険がある。

## 8. 外部ファイルと個人情報の保護

### 入力量の上限案（数値は未承認）

| 対象 | 初期候補 | 適用方法・限界 |
|---|---:|---|
| 入力ファイル | 10 MiB（10×1024×1024 bytes） | File.sizeで全読取前に検査。復号・展開機能は初版なし |
| メモ | 10,000件（通常＋ゴミ箱） | 個別文字数制約も併用 |
| タグ | 5,000件 | 名前一意性と関連整合性も検査 |
| 関連 | 100,000件 | 同値重複・孤立関連を拒否 |
| 削除済みID | 100,000件 | 超過時は拒否。既存履歴を間引かない |
| JSON最大ネスト | 32階層 | 型検証より前の解析予算として強制する方式を選定 |
| 統合後候補JSON | UTF-8で16 MiB | ファイル上限とは別。現在データとの合計が上限を超えれば全体拒否 |

これらは同時に満たす必要があり、最大件数まで本文を埋め込める保証ではない。UTF-8バイト数、JS文字列長、localStorageの容量計算は区別する。実機・モバイルの時間／メモリ・実容量検証後に数値を承認する。既存データが上限を超える場合の救出用エクスポートも未決で、勝手に切り詰めない。

### 解析・表示・ファイル名

- 拡張子やMIMEだけで信頼しない。初版は`.json`を対象にし、MIMEは参考情報、最終判定はサイズ・文字コード・専用形式・内容検証で行う案。名前が適切でも不正内容なら拒否する。
- 入力ファイル名は保存キー・パス・HTML・URLへ流用しない。制御文字、パス区切り、双方向表示制御などの扱いを決め、表示は制限したプレーンテキストにする。出力名はアプリ生成の固定prefix＋安全なUTC日時＋`.json`とし、メモタイトルを使わない。
- UTF-8を厳格に復号し、不正バイトを置換文字で救済しない。BOM・別文字コードの許容範囲は形式仕様で固定する（初版はBOMなしを推奨）。
- 現行JSON.parseは同名キーの重複を検出できず、最後の値が残る。外部バックアップでは同名JSONキーも拒否する案とし、深度・入力予算と合わせた解析方式を別途選定する。正規表現だけでJSON構文を検査しない。新パーサ依存を追加する場合は事前承認が必要。
- 解析結果は全階層で許可キーだけを受理し、`__proto__`・`constructor`・`prototype`等を未知項目として拒否する。任意キーの再帰マージ、Object.assignによる未検証値の反映、evalをしない。検証器で明示的に再構築し、Map/Set等でUUIDを照合する。
- タイトル・本文・タグ名はテキストとして表示し、innerHTML・属性・スタイル・リンク先へ展開しない。バックアップ内に外部資産URLを持つ形式を採用せず、外部通信を行わない。
- 元JSON・本文・タグ名・ファイル名・旧キー・legacySnapshot・元例外メッセージをログ／分析送信／PR／テスト成果物へ出さない。エラーは固定コードと必要最小限の構造的な位置情報だけとする。
- 生ファイル、候補、承認材料はタブ内メモリだけ。ドラフト保護とは分けて、取消・終了時に不要な参照を解放しBlob URLもrevokeする。メモリの完全消去やOSスワップ等の消去は保証しない。
- 出力ファイルは本文・タグ・削除IDを含む平文の個人情報で、削除後もファイルやクラウド同期フォルダーに残り得る。共有・保存場所・利用者自身の管理責任を保存開始前に案内する。Gitへ登録しない。

### 暗号化

初版はアプリ内暗号化を対象外とする案。平文であることを明示し、利用者の明示保存以外で外部送信しない。暗号化を必要条件とするかはオーナー判断。将来実装する場合は暗号方式・鍵導出・パスワード忘失・認証付き暗号・復号前後のサイズ制限・相互運用を別設計とし、独自暗号や単なるBase64を暗号化と表示しない。

## 9. 履歴保護の保証範囲とロールバック

- 保持できる履歴は、現在領域と有効なバックアップに残っているものの和集合まで。サイトデータ消去・全領域喪失・履歴欠落ファイルへの手編集で失われた情報を推測して再生できない。
- 空のv3が「初めての利用」か「履歴消失後」かは現行形式だけでは証明できない。別端末／別ブラウザへの初期復元は、残存履歴を確認できる同一領域への統合と保証範囲が違う。初版でのサポート可否を別途承認する。
- バックアップの作成日時・sourceStorageVersionを出所証明にしない。任意ファイルをv3更新の導入元許可へ転用しない。
- 復元後もv3と履歴を理解する書込停止保守版を公開前の必須条件とする。旧v2コードへ戻してもデータはv3のまま停止し、自動逆変換しない。コード復帰とデータ復旧を分離する。
- 旧JSは旧キーへ書ける。復元で旧値へ同期・逆変換せず、既存の新旧分岐／旧タブ停止問題を解消済みとしない。
- 共通Web Locksに従わない同一originコード、最終照合後の外部書込、ABA、電源断・ディスク障害までを原子的に防ぐ保証ではない。

## 12. 実装PRの分割案と完了条件

設計承認後、関連性を保って次の2単位を推奨する。PR番号は将来の採番に従う。

1. **バックアップ形式・出力・読取専用復元プレビュー**：純粋な検証・計画、承認済みパーサ／上限、File/Blob境界、合成メモリの隔離UI・ダウンロード試験。適用書込は提供しない。形式・全衝突規則・個人情報非露出をレビューできる状態を完了条件とする。
2. **承認付き追加型復元・競合／障害検証**：専用commit、privateプラン／確認、A案共有、結果不明時の再診断、所有環境の実Web Locks・複数タブ・容量・読戻し・保守停止。全必須テストと既存回帰を通し、未検証事項を引き継ぐ。

完全置換、新IDインポート、暗号化、v2救出、バックアップの世代管理、初期復元／別領域管理、クラウド連携はこの2単位へ混在させず別判断とする。公開資産・実ユーザーデータに触れず、Draftレビュー・人間の受入・公開承認を分離する。
