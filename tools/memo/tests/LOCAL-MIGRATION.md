# ローカル移行基盤：承認済み契約とテスト方針

根拠は[統合仕様§3・5](../doc/v1.1.0/memo_v1_1_implementation_review8.md)、[第二弾の読み取り契約](READ-VALIDATION.md)、第三弾の安全設計に対するユーザー承認。正式資料原本は変更しない。

## 実行境界

保存先・Web Locks・UUID生成器は注入する。実際のnavigator.locksを渡せる排他ラッパーを用意するが、モジュール読込でnavigatorやlocalStorageにアクセスせず、既存画面にも接続しない。テストは合成データとメモリ内保存先だけを使用する。

- 全処理で共通の排他ロック名を使用する。Web Locks非対応・取得失敗時は書込禁止。ロックの強制取得・タイムアウト再試行・代替の無排他書込は行わない。
- inspectはロック内の読取と判定のみ。新旧キーなしならempty、旧値のみならmigration-required、整合したpendingならrecovery-ready、complete/not-requiredならexistingを返す。
- migrateは確認時の旧生文字列を要求する。ロック取得後に旧値が変わっていれば再承認が必要で、書き込まない。既存の新値があれば検証して保護し、pendingは復旧操作を別途要求する。
- recoverは確認時の旧生文字列とpending生文字列を要求し、ロック内で両方の一致と移行内容を再検証する。inspectや起動だけでは復旧書込しない。
- 旧形式を全件検証してからUUIDを発行し、旧IDの再利用・新UUIDの重複は拒否する。内容・順序・日時の原表現を保持し、revision=1、ピン/削除/lastRequestId=null、タグ/関連空を要求する。
- 新規移行はpending書込→旧値と新値の読戻し照合→complete書込→再照合。各書込直前にも新旧値を再確認する。自分が書いたJSONの読戻しは生文字列の完全一致と構造・整合性を検証する。
- 旧キーへのsetItem、removeItem、clearは実装しない。新旧キーが両方ない場合もnot-requiredを書かない。
- 失敗時は全体停止し、固定理由コード・処理段階・再観測した残存状態を返す。生文字列や元例外はエラーへ含めない。書込を試行した後の失敗はunverifiedとし、成功・消去・ロールバック・再試行を断定／実行しない。
- inspectの承認材料や成功データには利用者データが含まれるため、呼出側はログへ出さない。停止結果の残存状態は失敗後の観測であり、永続的な状態保証ではない。

## テスト観点

| 観点 | 期待する結果 |
|---|---|
| 正常移行、空の旧配列 | 順序と文字列保持、UUID再発行、pending/completeの2書込、旧キー不変 |
| 新旧キーなし | empty、書込0件 |
| キャンセル・未承認 | inspectのみでは書込・UUID生成0件 |
| Web Locks非対応・取得失敗 | 操作を実行せず停止、書込0件 |
| 排他・待機中の変更・二重移行 | ロック内で再確認し、既存新値を上書きしない |
| 旧値不正・生成器失敗・UUID重複/再利用 | pending書込前に全体停止、補正・再生成なし |
| pending照合 | 旧生文字列、全項目、順序、ID一意、revision/初期値、タグ/関連、承認した新生文字列が一致する場合だけ復旧 |
| 障害・中断 | 各書込/読戻し失敗を注入し、成功扱いせず残存状態を報告。自動再試行や削除なし |
| 不変性・秘匿 | 入力を補正せず、エラーに本文・タイトル・タグ・旧生文字列・元例外を含めない |

既存337件を維持し、型チェックと全Vitestを実行する。ブラウザの複数タブ・実Web Locks・容量制限の実挙動は未検証。ロック外の旧版JS書込は防止できず、複数キーの原子性も保証しない。観測の間に行われて元に戻った変更（ABA）や、最終読戻し後の書込は検出できない。実ブラウザ保存データの移行・UI・通常CRUDは後続工程。
