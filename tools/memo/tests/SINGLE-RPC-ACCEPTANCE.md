# single-rpc 認定前ゲート

## 結論

現行の製品senderは、通信なし・注入fetchの境界であり、すべての応答を`unverified`として返す。`single-rpc`への昇格処理は実装しない。HTTP status、JSON本文、SQLSTATEらしい値、偽fetchの成功だけでは実経路の認定条件を満たさない。

## 認定条件

`single-rpc`を将来許可するには、少なくとも次を同じ実行経路について証拠付きで確認し、オーナーが承認する必要がある。

| 条件 | 通信なしで確認できる範囲 | 実接続で必要な証拠 |
| --- | --- | --- |
| 固定送信先 | senderが承認済みoriginとRPCパスだけを生成 | 本番/開発環境の接続先が意図したプロジェクトであること |
| RPC・引数 | 8 RPC、完全なキー集合、RPC別のUUID/文字列/revision/配列/action検証 | SQL署名、PostgREST引数、DB側正規化の一致 |
| HTTP形式 | POST、`redirect:error`、1回の注入fetch、15秒期限 | 実fetch・SDK・プロキシが再送・中継・本文差替えをしない根拠 |
| 認証 | Bearerを結果へ漏らさず、sender生成時の値を固定 | C03の現在世代・所有者・期限と実セッションの対応 |
| 応答 | URL/status/204本文/JSON構文を検証 | 応答がその1回の正式RPCから返ったこと、認証・所有者が対応すること |
| 結果分類 | C01が`unverified`を成功へ分類しない | PostgREST実版、RLS、RPC本文、要求台帳の実動作 |
| timeout/中断 | Abort要求と呼出側の15秒停止 | 実サーバーの処理停止・DB未実行を保証しないことを前提に結果不明扱い |

## 世代・結果不明の扱い

- 認証世代の確認はC03 `prepareRpc()` とC04 controllerの責務であり、sender単体で代替しない。
- 送信後に世代変更、通信断、timeout、本文読取失敗が起きた場合は結果不明。自動再送、ロールバック、`single-rpc`昇格を行わない。
- C04は古い応答を反映せず、書込操作の固定スナップショットを保持する。
- 個別削除、一括削除、タグ操作には正式な照合RPCがないため、保存用resolveを流用しない。

## 通信なしゲート

- [x] 全8 RPCの許可パスと完全キー集合
- [x] RPC別の意味型検証、未知キー拒否、配列長照合
- [x] 固定origin、POST、redirect拒否、1回送信、15秒期限
- [x] URL/status/本文/204検証と固定エラー
- [x] Bearer・config変更の非公開化
- [x] すべての応答が`unverified`であること
- [x] C01/C04で`unverified`を成功扱いしないこと
- [x] 偽fetchのみでの回帰テスト

## 実接続前の承認チェックリスト

1. 対象環境・origin・公開キーの確認（本番か開発かを明示）。
2. 実Authユーザー、合成データ、操作上限、停止担当者の承認。
3. SDK/fetch/プロキシの自動再試行・リダイレクト・中継・キャッシュ挙動の根拠。
4. SQL署名・RPC本文・RLS/GRANT・PostgREST応答の契約一致確認。
5. 成功応答を`single-rpc`と扱う実装変更のレビュー承認。根拠不足時は`unverified`を維持。
6. timeout、通信断、結果不明、所有者不一致時の後続書込停止と手動再診断手順。
7. 失敗時の証跡保全、再実行禁止、データ復旧判断。

## 未検証事項・停止条件

実Supabase/Auth/DB、実Bearer、RLS/GRANT、SQL/TS共通ベクトル、PostgRESTの実応答、実プロキシの再送・中継、DB処理の中断完了は未検証である。これらが確認できない状態で`single-rpc`へ昇格してはならない。実接続、SDK接続、製品UI/C05接続は別承認とする。
