# メモツール Ver1.1.0｜実装前の設計修正（第4レビュー案）

> **位置付け：実装案・未検証。** Codexの指摘を反映したもの。SQLはSupabaseに未実行。旧キーへの書込み禁止、クラウドとローカルの非同期・非同期切替禁止、明示的保存、未保存内容保持は既存合意を維持する。

## 1. データ構造と責務

- 共通ドメイン：`Memo`（`revision`、`lastRequestId`追加）、`Tag`（`revision`追加）、`MemoTagRelation`。
- localStorageは単一キー `myhomepage.memo.data.v2` に `version:2`、`migration`、`memos/tags/memoTags` を保存。新キーの旧案はまだ本番未配布の前提。すでに利用者のv2データが存在するなら、**無断でスキーマ変更せず別途互換移行を設計**する。
- Supabaseは `memos/tags/memo_tags` の3テーブル。DB行（snake_case、`user_id`を含む）とドメイン型（camelCase）をアダプタで相互変換。`user_id` は認証情報からDB側で確定し、クライアントが指定しない。
- 新規メモの `revision=1`。本文、タグ関連付け、ピン、ゴミ箱移動、復元を変更するたびに revision を増やす。`updatedAt` と `pinnedAt` はサーバー時刻（クラウド）／操作時刻（ローカル）で更新。新規作成と既存更新は区別し、既存IDへの無条件upsertは禁止。
- **保存済みと編集中を分ける。** 編集画面に保持することは永続化を意味しない。再読み込み・ブラウザ終了で下書きが失われる可能性を許容する。`beforeunload` 警告はブラウザ依存。

## 2. クラウドの競合と不明な保存結果（重大1・4）

1. 画面で読み込んだ `revision` と、1回の操作につき一意の `requestId` を保持。新規保存時は最初に生成した `id` と `requestId` を再試行時も使う。
2. `memo_save` RPCは、作成時には既存IDがないこと、更新時には行が存在しrevisionが一致しゴミ箱外であることを検査する。本文・タグを同一トランザクションで確定し、更新後の行を返す。
3. ピン・ゴミ箱移動・復元もrevisionを照合し、対象なし・競合時は成功と表示しない。完全削除はゴミ箱内かつrevision一致の場合のみ。
4. 通信切断で応答がない場合、**保存失敗と断定しない**。同じID・requestIdの台帳結果を取得し、永続的なリクエスト台帳の操作種別・対象ID・期待revision・本文・タイトル・正規化済みタグID集合・保存時結果が、送信時に凍結した要求と一致する場合のみ、その要求の成功を確定。一致しない／存在しない／照合できない場合は、入力を保持して競合・結果不明として案内する。照合不能な間は新しいIDやrequestIdで自動再送しない。
5. 別端末が先に編集した場合は自動上書きせず、編集中の内容を保持して「最新状態を確認して再編集」を案内。自動マージはしない。
6. **完全削除の応答消失**は、再読込で対象不在なら削除済みと扱う。ただしユーザー権限や通信障害で不在と断定できない場合は結果不明のままにする。

## 3. localStorageの競合（重大2）

- すべての書込み（メモ・タグ・関連・移行・削除）を同じ名前の `navigator.locks.request('memo-tool-v2-write', {mode:'exclusive'}, ...)` で排他。ロック中に**新キーを再読込→形式検証→revision照合→単一JSON保存→読戻し**。
- `storage` イベントは別タブへの通知に使用するが排他制御の代用にはしない。
- Web Locks APIが使えないブラウザでは、複数タブでの安全性を保証できないため**書込み・移行を無効化し理由を表示**する。読取りのみ可能な場合も旧キーを変更しない。
- ロック取得・保存・読戻し失敗時は成功扱いしない。保存先変更中の非同期応答は、開始時の保存先・ユーザー・画面セッションと一致する場合にのみ反映。保存中は切替／ログアウトを操作不能にするか完了まで待たせる。
- 注：旧版JSが開いたままの場合、そのコードはロックに参加しない。**移行前に旧タブを閉じる案内**を表示する。旧版との並行使用はサポートしない。

## 4. 移行の確定手順（重大3）

1. 旧キー `myhomepage.memo.items.v1` は**読み取り専用**。新キーがすでにあれば勝手に上書きしない。
2. 新キーなし＋旧キーありなら移行確認。キャンセルなら両キーを変更せず次回起動時に再提示。
3. 承認後、Web Lock内で新キー不存在を再確認し、旧キーの**生文字列**をスナップショットとして取得。厳格に全件検証（後述）。不備があれば1件でも全体中断、項目・理由を表示。
4. 新UUIDを全件生成。`text→body`、日時と順序を維持、ピン／ゴミ箱なし、revision=1、lastRequestId=null、タグなし。新キーに `migration.status='pending'` と旧キー生文字列 `legacySnapshot` を**同一JSON**で保存する。
5. 読戻し後、`legacySnapshot` と現在の旧キーが一致するか、元配列の各要素と変換後の各要素が対応するか、UUID・件数・順序・日時が正しいかを検証。
6. 成功したら新キーの `migration.status='complete'` に変更し、再度読戻して検証して初めて通常起動。旧キーは残す。
7. `pending` で中断・再起動した場合は、通常利用せず、Web Lock内で旧キーとの照合を再実行。合格すれば `complete` に確定。不一致・検証失敗なら自動削除／再移行せず復旧案内。
8. `complete` でも構造破損があれば起動停止。旧キーが後で変更されても勝手にマージしない（別タブ旧版利用の注意を表示）。

### 旧データの検証

- JSON配列であること。全要素の `id/title/text/createdAt/updatedAt` が存在し、型はstring。IDは非空・配列内一意。追加の未知プロパティも中断して報告。
- 日時は厳密なISO 8601インスタントで、解析・再表現時に意図しない補正が起きないこと。曖昧なローカル日時は拒否。
- 旧タイトルは**1〜100コードポイント・前後の半角空白なし・空白のみ不可**、本文は0〜10000コードポイント。欠落・超過・禁止文字・不正なUnicodeは全体中断。タイトル空＋本文ありも旧形式のままでは移行中断（勝手に「無題」にしない）。
- 旧版が許したデータでも新制約に合わなければ移行できない。画面で「何件目／項目／理由」を案内し、旧データは変更しない。
- 日時・UUID・参照先の存在・重複・Unicodeの実行時検証は必須。単なるTypeScript型注釈では検証にならない。

## 5. ゴミ箱とタグ（重大5）

- **ゴミ箱一括削除は原子的**。確認時点のゴミ箱の全IDとrevisionを渡し、サーバーが現状と完全一致した場合だけ全件削除。復元・新たな削除が挟まった場合は競合エラーで何も消さず、再読込を案内。
- SQLは同一ユーザーの全メモ更新・削除・一括削除を**共通のトランザクションロック**で直列化する設計案。直接テーブル書込みは禁止し、RPCだけを公開する。
- ローカルも同じWeb Lock区間内でスナップショット照合後に単一JSONを更新。
- タグ削除時は通常メモ・ゴミ箱内メモ双方の関連を外す。タグ自体は使用件数0でも保持される。タグの使用件数は**ゴミ箱を除いた通常メモの関連件数**とする（ユーザー確定）。
- タグ名はユーザーごとに大小文字を区別せず一意。DBの `lower()` を最終判定とし、ローカルはUnicodeの大文字小文字変換差に注意。完全一致を保証するなら別途正規化仕様と実DB照合が必要。

## 6. 入力と画面設計の整合

- タイトル入力は前後空白を除去し、空なら本文があるとき「無題」。タイトル・本文とも空白だけなら保存禁止。本文の空白は保持。タイトル100、本文10000、タグ30コードポイント。
- DB `btrim()` とJS `trim()` は完全一致しないため、**実装時に検証規則を1つに統一**すること。レビュー用SQLは半角空白基準の最低限のDB制約で、JS側の厳密な検証を別途必須とする。NUL、孤立サロゲート、制御文字を検証する。
- 一覧の📌は表示のみ。**ピン操作はカードの︙**。一覧の複製も︙。**詳細の複製は独立ボタン**。詳細からの複製は新規編集・未保存、ピンを引き継がない。
- タグ選択は複数OR、検索語はタイトル／本文／タグ名の部分一致、両条件はAND。ピン優先、ピン内は `pinnedAt` 降順。検索・並び替え・スクロール位置を一覧復帰時に保持。
- 保存失敗・競合時は編集中の内容を保持。通信断時にクラウド→ローカル自動切替しない。ログアウト・保存先切替・離脱は未保存確認。ブラウザ終了後の下書き復元は保証しない。
- 音声認識未対応／拒否／失敗はエラーを表示して手入力を継続可能。文字数超過の追記は確定保存しない（入力欄の扱いはUIテストで確認）。音声ファイルは保存しない。
- PC／スマホの共通ヘッダー・フッターを維持。スマホでキーボード表示時も保存ボタンを操作できるかPlaywright／実機で検証。**図にないエラー画面・ゴミ箱操作は既存合意の仕様で実装**し、仕様追加しない。

## 8. 第2レビュー重大指摘への追加対策（第4レビュー案）

### A. 完全削除後の作成要求再送
- `memo_id_registry` は一度使われた `(user_id,memo_id)` を永久削除後も保持する。新規作成RPCは登録できた場合のみメモ作成し、再利用IDは拒否する。
- `memo_requests` は `requestId` ごとの操作と保存内容・結果を同一トランザクションで記録。応答消失→完全削除→同じ作成要求再送でも、台帳から**元の成功結果**を返し、メモを再作成しない。
- 「以前成功した」ことと「現在も存在する」ことは別。台帳の成功結果でUIに現存を断定せず、必要なら再読込する。台帳保持期間・ユーザー削除時の扱いは運用前に評価。

### B. requestIdの厳密な同一性
- requestIdは**ユーザー操作1回につき1つ**、別操作で再利用禁止。DBで `operation`、`memo_id`、`payload`（期待revision、タイトル、本文、タグIDの正規化集合）を照合し、不一致ならエラー。
- 通信結果不明時の編集内容は保持する。送信済みスナップショットは凍結し、編集中の最新ドラフトと区別。編集が進んだ場合も元の送信要求を新内容で再送しない。
- `memo_resolve_request` が返す記録をアダプタが凍結スナップショットと照合する。未記録でも**未実行と断定しない**（通信・権限・遅延中の可能性）。照合不能は `unknown`、明示的に未実行を証明できた場合のみ `not-applied`。
- RPC保存結果はメモとタグIDを**同一トランザクションでJSONとして返す**。`load()` の複数SELECTは異なる時点が混ざり得るため、スナップショットRPCを追加するか、取得前後のrevision・タグ変更世代を照合する方式を実装前に選定する。

### C. 不正な引数
- 状態変更の `p_action is null`、`p_id is null`、`p_expected_revision` がnull/0/負数を拒否。保存・完全削除・タグ操作も同様に入口検証する。
- 入力文字数・Unicode・空白の検証はSQLとTSで**まだ統一未完了**。クライアントのみの検証はDBの防御として不十分。全面実装前に確定・DBテストが必要。

### D. タグ削除のrevision
- タグ削除RPCは関連するメモ（ゴミ箱内も含む）のrevisionと更新日時を同じトランザクションで増やしてからタグ削除する。既存編集中のメモ保存はrevision競合になる。
- ローカルでもタグ削除時は関連メモrevisionを増やす。タグ名変更だけではメモのタグID集合は変化しないため、メモrevisionは増やさない。

### 移行・削除・UIの補足
- 旧キーなし・新キーなしの新規利用は `migration.status='not-required'` で初期化。旧データを移行した状態とは区別。ロック内で旧キー不存在を再確認する。
- ゴミ箱一括削除の応答不明時は**確認時のID集合だけ**を再取得し、対象全件が存在しないことを確認できた場合に成功とする。新たにゴミ箱に入ったメモを再送で削除しない。再送前にはスナップショットの一致確認をやり直す。
- タグ件数は通常メモだけ。ゴミ箱内の関連自体は維持し、復元で再集計する。
- 画面補足：競合時は「最新状態を確認」／「編集内容を保持して戻る」。結果不明時は「保存結果を再確認」。移行失敗時は「旧データは変更されていません」を表示し、再読込・復旧案内。スマホも共通フッターを維持する。

### 実装ゲート（継続）
- **本SQLは未実行・未検証。** 特にDB関数権限、複数テーブル読取の整合性、入力規則、タグ削除競合、削除要求の応答消失の契約を再レビュー・テストするまで全面実装しない。
- 追加テスト：作成→応答消失→完全削除→再送、requestId内容/操作混用、null操作、タグ削除→古いrevision保存、台帳成功だが現存しない、Web Locksと移行復旧、同時読み込み時の整合性。


## 9. 第3回Codexレビューへの対応（review4）

**本ファイルとSQL/TSは第4レビュー用の草案であり、実行・検証していない。** 前回の重大指摘A/B/Dは設計上改善したが、実DBの保証ではない。

### ユーザー確定：完全削除のデータ最小化
- 完全削除後、`memos`行と`memo_tags`関連を削除し、要求台帳の`result`に含まれるタイトル・本文・タグID等も同一トランザクションで消去する。`memo_id_registry`には使用済みメモIDを残す。
- `memo_requests`には要求ID、ユーザーID、メモID、操作種別、**照合用ハッシュ**、削除済み印のみ残す。保存要求の元本文・タイトル・タグ配列を平文で残さない。既存要求を再送したとき、削除後は**本文を含まない「過去に適用済み・現在は削除済み」**を返す。新規作成として復活させない。
- ハッシュは暗号化でも完全匿名化でもない。元の内容を推測できる余地やDBバックアップ・ログ・履歴は別途評価が必要。「DBの現行行から消去」と「すべてのバックアップから即時消去」は区別する。ハッシュ生成の完全一致はDBテストで確認する。

### 修正・追加
- `pg_catalog.coalesce`を`coalesce`に修正。
- `memo_save`は要求の形式と正規化タグ集合を検証し、台帳照合を**タグの現在の存在確認より先**に行う。初回要求の場合のみタグの所有権・存在を確認する。
- `memo_load_snapshot`はメモ・タグ・関連を**1つのSQL文**で取得する案。単一文スナップショットとRLS/権限をテストDBで確認する。読み取り結果はsnake_caseのDB型からTSドメイン型に変換する。
- revisionは1〜`Number.MAX_SAFE_INTEGER`（9007199254740991）を共通上限とし、DB制約と各RPC入口で拒否する。増分上限到達時はDB制約によりトランザクション全体を失敗させる。
- タグ保存と一括削除のnull/範囲/一次元配列の入口検証を補強。`emptyTrash`のrequestIdは**クライアント内の操作識別用のみ**、SQL台帳に記録しない。応答消失時は元の確認スナップショットだけを照合し、新たにゴミ箱に入ったメモは削除しない。
- 過去の保存成功が確認されても現在のメモの存在や同一内容は保証されない。編集中ドラフトを自動消去・自動上書きせず、最新状態の確認を促す。`previously-applied-deleted`は保存済み・現存として表示しない。
- タグ使用件数は**通常メモだけ**を集計し、ゴミ箱内の関連は保持する（既存の確定仕様）。

### なお全面実装前に解決すべき事項
1. **Unicode/空白/制御文字/大小文字の統一**：`trim()`、`btrim()`、`lower()`は同じ規則ではない。画面・ローカル・DBの共通仕様を確定し、SQL制約と実行時バリデータを実装・テストする。特に本文の改行を禁止しないこと。現在のSQLは**未完成**。
2. **ハッシュ・台帳の整合**：再送の同一性を操作・ID・期待revision・タグ集合・本文で判定し、削除後に平文を残さない。削除済みreceiptの戻り値と`memo_resolve_request`の戻り値を統一する。再送の順序や同時実行をテストする。
3. **DB検証**：`extensions.digest`の存在、`SECURITY DEFINER`所有者、anon/PUBLICへのEXECUTE、直接DML、RLS、同時トランザクション、空配列、制約、SQLのコンパイルを使い捨てDBで検証。本番DBには適用しない。
4. **画面遷移**：競合・結果不明時の「編集内容を保持して戻る」は同一タブのメモリ内ドラフトを保持するだけであり、ページ更新・終了後の復元は保証しない。保存先切替やログアウトでは未保存確認。復旧案内は元データを破壊しない再読込／再検証の導線に限定。
5. **プライバシー説明**：使用済みIDと照合ハッシュの長期保持、バックアップ等の保持可能性を利用者向けに説明する。ユーザーアカウント削除時はFK cascadeで内部台帳も消える想定だが、実DBで確認する。
