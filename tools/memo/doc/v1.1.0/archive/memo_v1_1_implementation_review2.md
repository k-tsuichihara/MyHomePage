# メモツール Ver1.1.0｜実装前の設計修正（第2レビュー案）

> **位置付け：実装案・未検証。** Codexの指摘を反映したもの。SQLはSupabaseに未実行。旧キーへの書込み禁止、クラウドとローカルの非同期・非同期切替禁止、明示的保存、未保存内容保持は既存合意を維持する。

## 1. データ構造と責務

- 共通ドメイン：`Memo`（`revision`、`lastRequestId`追加）、`Tag`（`revision`追加）、`MemoTagRelation`。
- localStorageは単一キー `myhomepage.memo.data.v2` に `version:2`、`migration`、`memos/tags/memoTags` を保存。新キーの旧案はまだ本番未配布の前提。すでに利用者のv2データが存在するなら、**無断でスキーマ変更せず別途互換移行を設計**する。
- Supabaseは `memos/tags/memo_tags` の3テーブル。DB行（snake_case、`user_id`を含む）とドメイン型（camelCase）をアダプタで相互変換。`user_id` は認証情報からDB側で確定し、クライアントが指定しない。
- 新規メモの `revision=1`。本文、タグ関連付け、ピン、ゴミ箱移動、復元を変更するたびに revision を増やす。`updatedAt` と `pinnedAt` はサーバー時刻（クラウド）／操作時刻（ローカル）で更新。新規作成と既存更新は区別し、既存IDへの無条件upsertは禁止。
- **保存済みと編集中を分ける。** 編集画面に保持することは永続化を意味しない。再読み込み・ブラウザ終了で下書きが失われる可能性を許容する。`beforeunload` 警告はブラウザ依存。

## 2. クラウドの競合と不明な保存結果（重大1・4）

1. 画面で読み込んだ `revision` と、1回の操作につき一意の `requestId` を保持。新規保存時は最初に生成した `id` と `requestId` を再試行時も使う。
2. `memo_save` RPCは、作成時には既存IDがないこと、更新時には行が存在しrevisionが一致しゴミ箱外であることを検査する。本文・タグを同一トランザクションで確定し、更新後の行を返す。
3. ピン・ゴミ箱移動・復元もrevisionを照合し、対象なし・競合時は成功と表示しない。完全削除はゴミ箱内かつrevision一致の場合のみ。
4. 通信切断で応答がない場合、**保存失敗と断定しない**。同じIDの現状を再取得し、`lastRequestId` が一致するなら保存成功を確定。一致しない／存在しない／照合できない場合は、入力を保持して競合・結果不明として案内する。照合不能な間は新しいIDやrequestIdで自動再送しない。
5. 別端末が先に編集した場合は自動上書きせず、編集中の内容を保持して「最新状態を確認して再編集」を案内。自動マージはしない。
6. **完全削除の応答消失**は、再読込で対象不在なら削除済みと扱う。ただしユーザー権限や通信障害で不在と断定できない場合は結果不明のままにする。

## 3. localStorageの競合（重大2）

- すべての書込み（メモ・タグ・関連・移行・削除）を同じ名前の `navigator.locks.request('memo-tool-v2-write', {mode:'exclusive'}, ...)` で排他。ロック中に**新キーを再読込→形式検証→revision照合→単一JSON保存→読戻し**。
- `storage` イベントは別タブへの通知に使用するが排他制御の代用にはしない。
- Web Locks APIが使えないブラウザでは、複数タブでの安全性を保証できないため**書込み・移行を無効化し理由を表示**する。読取りのみ可能な場合も旧キーを変更しない。
- ロック取得・保存・読戻し失敗時は成功扱いしない。保存先変更中の非同期応答は、開始時の保存先・ユーザー・画面セッションと一致する場合にのみ反映。保存中は切替／ログアウトを操作不能にするか完了まで待たせる。
- 注：旧版JSが開いたままの場合、そのコードはロックに参加しない。**移行前に旧タブを閉じる案内**を表示する。旧版との並行使用はサポートしない。

## 4. 移行の確定手順（重大3）

1. 旧キー `myhomepage.memo.items.v1` は**読み取り専用**。新キーがすでにあれば勝手に上書きしない。
2. 新キーなし＋旧キーありなら移行確認。キャンセルなら両キーを変更せず次回起動時に再提示。
3. 承認後、Web Lock内で新キー不存在を再確認し、旧キーの**生文字列**をスナップショットとして取得。厳格に全件検証（後述）。不備があれば1件でも全体中断、項目・理由を表示。
4. 新UUIDを全件生成。`text→body`、日時と順序を維持、ピン／ゴミ箱なし、revision=1、lastRequestId=null、タグなし。新キーに `migration.status='pending'` と旧キー生文字列 `legacySnapshot` を**同一JSON**で保存する。
5. 読戻し後、`legacySnapshot` と現在の旧キーが一致するか、元配列の各要素と変換後の各要素が対応するか、UUID・件数・順序・日時が正しいかを検証。
6. 成功したら新キーの `migration.status='complete'` に変更し、再度読戻して検証して初めて通常起動。旧キーは残す。
7. `pending` で中断・再起動した場合は、通常利用せず、Web Lock内で旧キーとの照合を再実行。合格すれば `complete` に確定。不一致・検証失敗なら自動削除／再移行せず復旧案内。
8. `complete` でも構造破損があれば起動停止。旧キーが後で変更されても勝手にマージしない（別タブ旧版利用の注意を表示）。

### 旧データの検証

- JSON配列であること。全要素の `id/title/text/createdAt/updatedAt` が存在し、型はstring。IDは非空・配列内一意。追加の未知プロパティも中断して報告。
- 日時は厳密なISO 8601インスタントで、解析・再表現時に意図しない補正が起きないこと。曖昧なローカル日時は拒否。
- 旧タイトルは**1〜100コードポイント・前後の半角空白なし・空白のみ不可**、本文は0〜10000コードポイント。欠落・超過・禁止文字・不正なUnicodeは全体中断。タイトル空＋本文ありも旧形式のままでは移行中断（勝手に「無題」にしない）。
- 旧版が許したデータでも新制約に合わなければ移行できない。画面で「何件目／項目／理由」を案内し、旧データは変更しない。
- 日時・UUID・参照先の存在・重複・Unicodeの実行時検証は必須。単なるTypeScript型注釈では検証にならない。

## 5. ゴミ箱とタグ（重大5）

- **ゴミ箱一括削除は原子的**。確認時点のゴミ箱の全IDとrevisionを渡し、サーバーが現状と完全一致した場合だけ全件削除。復元・新たな削除が挟まった場合は競合エラーで何も消さず、再読込を案内。
- SQLは同一ユーザーの全メモ更新・削除・一括削除を**共通のトランザクションロック**で直列化する設計案。直接テーブル書込みは禁止し、RPCだけを公開する。
- ローカルも同じWeb Lock区間内でスナップショット照合後に単一JSONを更新。
- タグ削除時は通常メモ・ゴミ箱内メモ双方の関連を外す。タグ自体は使用件数0でも保持される。タグの使用件数は**ゴミ箱を含む全関連メモ数**として表示する（設計補足・要UI最終確認）。
- タグ名はユーザーごとに大小文字を区別せず一意。DBの `lower()` を最終判定とし、ローカルはUnicodeの大文字小文字変換差に注意。完全一致を保証するなら別途正規化仕様と実DB照合が必要。

## 6. 入力と画面設計の整合

- タイトル入力は前後空白を除去し、空なら本文があるとき「無題」。タイトル・本文とも空白だけなら保存禁止。本文の空白は保持。タイトル100、本文10000、タグ30コードポイント。
- DB `btrim()` とJS `trim()` は完全一致しないため、**実装時に検証規則を1つに統一**すること。レビュー用SQLは半角空白基準の最低限のDB制約で、JS側の厳密な検証を別途必須とする。NUL、孤立サロゲート、制御文字を検証する。
- 一覧の📌は表示のみ。**ピン操作はカードの︙**。一覧の複製も︙。**詳細の複製は独立ボタン**。詳細からの複製は新規編集・未保存、ピンを引き継がない。
- タグ選択は複数OR、検索語はタイトル／本文／タグ名の部分一致、両条件はAND。ピン優先、ピン内は `pinnedAt` 降順。検索・並び替え・スクロール位置を一覧復帰時に保持。
- 保存失敗・競合時は編集中の内容を保持。通信断時にクラウド→ローカル自動切替しない。ログアウト・保存先切替・離脱は未保存確認。ブラウザ終了後の下書き復元は保証しない。
- 音声認識未対応／拒否／失敗はエラーを表示して手入力を継続可能。文字数超過の追記は確定保存しない（入力欄の扱いはUIテストで確認）。音声ファイルは保存しない。
- PC／スマホの共通ヘッダー・フッターを維持。スマホでキーボード表示時も保存ボタンを操作できるかPlaywright／実機で検証。**図にないエラー画面・ゴミ箱操作は既存合意の仕様で実装**し、仕様追加しない。

### 要注意（実装前に解消）

1. `memo_empty_trash` と全変更RPCの同時実行、`SECURITY DEFINER` の実権限はテストDBで確認。
2. `memo_save` の結果不明時に、タグを含む保存内容を読み戻して照合すること。`lastRequestId` だけで「現在も同じ内容」と決めつけない。
3. タグ名のUnicode大小文字判定、前後空白、文字数をローカルとクラウドで揃えるための具体的なバリデータは未実装。
4. UIのタグ使用件数（ゴミ箱を含む）は追加提案なので、ユーザー承認前に確定仕様とみなさない。
