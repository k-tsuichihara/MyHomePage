# メモツール Ver1.1.0：移行・保存の実装引き継ぎ仕様（改訂案）

## 1. 確定したユーザー要件
- 旧キー `myhomepage.memo.items.v1` は変更・削除しない。
- 新キーは `myhomepage.memo.data.v2`。クラウドへ自動同期・転送しない。
- 旧データを検出したらユーザー確認後に移行。キャンセル時は両キーとも変更しない。
- 全旧IDを新しいUUIDへ振り直す。元の配列順・タイトル・本文・日時は保持する。
- 欠落・不正値・重複ID・文字数超過などが1件でもあれば全体中断。補完・切り詰め・一部移行はしない。
- 失敗時は旧データを保持し、原因を表示する。移行成功時も旧データは保持する。

## 2. 旧形式の厳格な検証
- `JSON.parse` の結果を `unknown` として扱い、配列であることを確認する。
- 各要素はオブジェクト。`id`, `title`, `text`, `createdAt`, `updatedAt` がすべて文字列で存在すること。
- `id` は空でなく、同じ配列内で重複しないこと。
- 日時は有効なISO 8601の日時文字列であること。**時刻を自動生成・補正しない**。
- `title` は1〜100文字（空白のみ不可）、`text` は0〜10,000文字。本文のみのメモなど旧形式の実データが不適合なら移行を止めて報告する。
- 未知の追加プロパティは黙って捨てず、検出して報告・移行を中断する（旧コードが許容するため要注意）。
- 文字数はPostgreSQLの `char_length` と同等のUnicodeコードポイント数で判定する。
- 実際の旧データが上記条件を満たすかは未確認。移行前に匿名化した検証を推奨。

## 3. 移行の手順と復旧
1. 新キーの有無を先に確認。存在する場合は**正常・不正を問わず自動上書きしない**。正常なら新形式を利用。不正なら読み込みを停止して復旧案内。
2. 新キーがなく旧キーがある場合、移行確認ダイアログを表示。キャンセルしたら旧データを読み書きせず、次回起動時に再提示する。
3. 承認後、旧キーの生文字列を読み取り、全件検証。問題があれば何件目・どの項目かを示して中断。
4. 全件検証後、`crypto.randomUUID()` で各メモに新UUIDを付与し、`text` → `body`、`pinnedAt`/`deletedAt` → `null`。タグと関連付けは空配列。
5. 新形式をメモリ上で検証してから新キーへ保存。保存後に読み戻し、件数・順序・ID一意性・全フィールドの一致を検証。
6. 検証成功後にのみ新形式を通常利用する。旧キーの生文字列が変更されていないことも確認する。
7. 保存失敗・検証失敗時は通常起動を止め、エラー表示。新キーが残っていれば**自動削除や自動再移行をせず**、バックアップ確認の上で復旧を案内する。
8. 旧版を別タブで使うと旧キーに変更が加わりデータが分岐する。移行前に旧タブを閉じる案内を表示する。

## 4. 保存・競合時の共通動作
- メモの保存は明示的操作のみ。タイトル空・本文ありならタイトル「無題」。両方空なら保存不可。
- メモとタグ関連付けは**1回の論理操作として原子的に保存**する。ローカルは単一JSON書き込み、クラウドは同一DBトランザクションのRPC等を利用。
- 保存・復元・削除の成功表示は永続化成功確認後。失敗時は編集内容・画面上の対象を保持し、再試行可能にする。
- 保存先切り替え・ログアウト時の未保存変更は確認ダイアログで破棄またはキャンセル。
- 複数タブによる古い状態からの上書きを防止する。ローカルは保存前に最新状態を再読込して競合を検出、クラウドは更新日時等による楽観ロックを実装する。競合時は自動上書きせず再読込・再編集を案内。
- 新規ピン留めは先頭（`pinnedAt` 降順）。ピンアイコンは状態表示、操作は一覧の `︙` メニュー。

## 5. テスト受け入れ条件
- 正常データ（0件・複数件）、UUID一意性、内容・順序・日時維持、旧キー完全一致。
- キャンセル・再起動・新キー既存・新キー破損・保存容量不足・読み戻し失敗。
- 欠落項目・不正日付・重複ID・長文・未知プロパティ・JSON破損で全体中断。
- タグ保存失敗時にメモ本文だけ更新されないこと（ローカル／クラウド）。
- 別ユーザーのメモ・タグの参照／関連付けがRLSとFKで拒否されること。
- 複数タブ・複数端末で同時編集した場合、古い内容で上書きされないこと。
- 音声入力・一覧・詳細・ゴミ箱・タグ管理・レスポンシブUIは別の画面仕様書と突合すること。

## 6. 実装前に残る技術検証
- SQL RPCは**設計案**。テストSupabase環境で実際のRLS権限・更新件数・例外時ロールバックを検証する。
- DBの楽観ロックと原子的なゴミ箱一括削除は追加実装が必要。
- `updatedAt` をクライアントが指定する方式の整合性を検証し、必要ならDB側の時刻管理へ変更する。
- 旧データに未知の追加プロパティがある場合の停止方針は保守的な技術提案。実データを確認し、必要ならユーザーに確認する。
- 本文の空白を保持すること、Unicode文字数判定、タグ名のtrim/大小文字重複をローカルとDBで一致させる。
