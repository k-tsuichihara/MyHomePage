## ケース25の新規採用判断（2026-10-25）

- ユーザーが「完全削除のrevision競合拒否」を正式採用。既存の正式定義を復元したものではなく、今回新たに定義したケースとして記録する。
- 採用時点：ケース24が実DB PASSとの報告（run: 02b1a94b-d536-435b-9c38-1c21bec310a1）。計27/33件PASS。元の記録は変更しない。
- 目的：自分の専用メモがゴミ箱内・revision=2と直前に確認された状態で、expected_revision=1の個別完全削除が拒否されること。
- 新規専用タグ・関連付きメモを各1件作成し、trashでrevision 1→2へ進める。削除直前の確認は手動確認入力後に行い、全スナップショットをメモリ内で保持する。
- 期待拒否：HTTP409、JSON code PT409、message `not found or revision conflict`。エラー単独では原因を断定せず、直前状態と拒否後の全取得データ不変を組み合わせる。
- 正常終了時は専用メモ（ゴミ箱・revision=2）・タグ・関連各1件を残す。正しいrevisionで削除し直さない。内部台帳は直接未検証。
- 実装・構文・ローカル模擬/回帰検証のみ許可。実DB接続・実行は別途判断。ケース26〜30は未定義のまま。
- 手順・安全条件・根拠は [DELETE-CONFLICT-TEST.md](DELETE-CONFLICT-TEST.md)。ケース24の正常削除、ケース23の他ユーザー削除拒否とは区別する。
